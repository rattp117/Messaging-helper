## How it works

LINE never includes a display name inline on an inbound event (unlike Telegram's `message.from.first_name`), so `LineChannel.run()` now wraps the caller's `on_message`: for every inbound message it calls `_display_name_for(user_id)`, which checks the `users` row first (already-known name → no network call at all) and otherwise fetches `GET /v2/bot/profile/{userId}` **at most once per process per user** (tracked in an in-memory set), fail-open to `None` on any error. The resolved name is passed through as `on_message`'s existing `display_name` argument — from there, `core/access.py:handle_gate`'s pre-existing "unknown" branch (unchanged, built in v1.2.0 for Telegram) persists it to the `users` row and includes it in the owner's `access_request` notification, exactly as it already did for Telegram.

`core/access.py:execute_admin` calls `_resolve_admin_target_chat`, which (post-hardening) runs a 4-step pipeline: (1) an exact `chat_id` match against an EXISTING `users` row, any status, verified by a real DB lookup — never a shape guess; (2)/(3) an exact pending-display-name match and a `≥6`-char pending-id-prefix match, both merged into ONE candidate pool with step 1 (so a token that is simultaneously one real user's exact id AND a literal prefix of a different pending user's id is correctly AMBIGUOUS, not silently resolved); (4), reached only when nothing above matched, the legacy "pre-approve/pre-block a chat id that's never contacted the bot" row-creation flow — gated to a token that's both id-shaped AND long enough to be a real, complete id (a "U"-shaped token needs ≥33 chars; a numeric one has no such floor). `/approve` and `/block` now feed this pipeline the FULL typed tail (not just its first word), so a multi-word display name resolves as a whole. `_render_users_list` shows the same captured name, truncated via the existing `core/render_budget.py:truncate` helper.

## Known limitations

- ~~Multi-word display names can't be typed after `/approve`/`/block`.~~ **FIXED by the hardening pass (F4).** `core/commands.py:_match_access` now captures the FULL, outer-trimmed tail for `/approve`/`/block` — a multi-word name resolves as a whole. `/invite` is the one deliberate exception (still `_first_token`) — see below.
- **`/invite` still only takes the first whitespace-delimited token** (Archi's ruling scoped the F4 full-tail capture to `/approve`/`/block` only). It targets a chat id that has never contacted the bot, so there's no pending row to name-match against in the first place — no practical loss, and `tests/test_access.py::test_dispatch_invite_extra_garbage_still_takes_first_token` pins the asymmetry deliberately.
- **Numeric (Telegram-style) ids have no prefix-resolution affordance and no length floor on the legacy creation path**, unchanged from the original design: `_CHAT_ID_RE`'s `-?\d+` alternative matches any digit string, so a numeric token always resolves at step 1 (exact-id-exists) or step 4 (creation) — never step 3 (prefix). This is fine: Telegram ids are already short and readable; the whole feature (and the F1-F3 danger it fixed) is specific to LINE's own long, variable-length `U...` ids.
- **F7 (informational, not fixed):** `/users` still has no total-message-length structural cap (`core/render_budget.py:fit_within_budget`, used by `audit_view`/`history_view`, is not called here) — per-row truncation holds (AC5's own wording), but a very large user count (~120+, per Vera's own probe) can still overflow the shared 4096-char send budget. Not in Archi's ruling for this pass; left as a follow-up.
- Everything else in Archi's ruling (F1-F6) is implemented and tested; nothing from the ruling was intentionally left out.

**Root mechanism:** `_resolve_admin_target_chat`'s original ordering treated a bare `_CHAT_ID_RE` shape match (`target_chat` looking like `-?\d+` or `U[0-9A-Za-z]{16,40}`) as an already-complete, verified chat id and used it AS-IS — before any existence check, and before name/prefix resolution was ever attempted. Every CRITICAL finding traces back to this one unverified pass-through.

| Finding | Severity | Root cause | Fix |
|---|---|---|---|
