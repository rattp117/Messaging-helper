## How it works

`Channel` (the ABC every messaging integration implements) gained three additive, backward-compatible surface points: a `disable_notification` flag on `send` (payload-only change, defaulted off), a new `set_message_reaction` concrete default (mirrors the existing `send_image`/`send_actionable` degradation pattern), and a `scope_chat_id` keyword on `set_my_commands`. `TelegramChannel` implements all three for real against Bot API 7.0's `setMessageReaction` and the existing `setMyCommands`/`sendMessage` endpoints, and now also extracts each inbound message's `message_id` in `run()`, threading it as a fourth, trailing, defaulted argument through `on_message` (main.py) into `handle_inbound_message`'s new `inbound_message_id` parameter — plumbing only, not yet consumed by any logic. In parallel, `core/commands.py`, `core/audit.py`/`audit_view.py`, `core/i18n.py`, `core/release_notes.py`, and `config.py`/`config.toml` each got the minimal skeleton/vocabulary/config additions the four upcoming parallel modules (`quicklog`, `routines`, `backfill`, `riders`) need to build against without colliding on these same shared files.

- The `[notifications] silent_proactive` flag is defined and defaulted but **not yet wired** to any of the three proactive-send sites (`reminders.send_reminder`, `checkins.run_due_checkins`, `nudge.run_due_nudges`) — that's module `riders`' own scope (R-D1).
- `__init__.py:__version__` was deliberately **not** bumped to `"1.8.0"` in this pass — that's Archi's Phase 6.5 action, done once the full feature (all four modules + integration) is verified, per this project's established release choreography.
- No `help_log_cmd`/`help_routine_cmd` discoverability copy was added in this pass — SPEC-v1.8.md §6 lists `i18n.py`'s quicklog/routine keys as module-owned, disjoint (unlike v1.7's shared surface, which did pre-add `help_addhabit_cmd`/`help_delhabit_cmd` early); each owning module adds its own help-menu entry alongside its command matcher, a deliberate scope match with the spec's file-ownership table, not an oversight.

## Iteration log

No Luna↔Vera round happened in this session (direct dispatch, no Vera in the loop yet). While proving the exit-bar ("full suite green"), I found and fixed **two pre-existing, unrelated bugs**, both caused by real-clock drift since these tests were authored (today's date is 2026-08-25; both hardcode a fixed "today"):

- **Failure 1**: `tests/test_v15_integration.py::test_current_pinned_version_announces_to_active_users_today` failed with `AssertionError: assert '1.7.0' == '1.6.0'`.
  **Root cause**: exactly the same self-referential version-pin pattern `IMPL-v1.7-shared.md` already documented fixing once (that time: `"1.5.0"` → `"1.6.0"`). `__init__.py:__version__` was bumped to `"1.7.0"` at v1.7.0's Phase 6.5 release; this test's own hardcoded expectation was never updated afterward (the bump happens after Vera's pre-release run, a structural gap the prior IMPL doc already flagged as a recurring, expected pattern — not something introduced by v1.8 work). Confirmed unrelated to my shared-surface changes: I never touched `__init__.py` or this test file's surrounding logic, only the literal.
  **Fix**: updated the literal (`"1.6.0"` → `"1.7.0"`) and docstring, mirroring the prior Luna's exact precedent.
- **Failure 2 & 3**: `tests/test_v16_integration.py::test_nudge_fires_through_the_real_tick_for_an_enabled_almost_there_user` and `::test_nudge_and_20_00_checkin_both_fire_independently_without_interference` both failed (`assert 2 == 3`, `assert 3 == 4`) — the expected extra nudge/check-in message never arrived.
  **Root cause**: both tests log a habit entry through `_run(...)`, which inserts via the real, un-frozen `handle_inbound_message(clock=datetime.now)` — i.e. whatever the real "today" is. Both then call `nudge.run_due_nudges`/`checkins.run_due_checkins` with a clock hardcoded to `datetime(2026, 8, 24, 20, 0, 0)` — "today" when the test was authored. Once the wall clock crossed into 2026-08-25 (mid-session, per this session's own date-change notice), the log landed on 08-25 while the nudge/check-in tick looked for "today" on its own frozen 08-24, found nothing, and never fired. Confirmed unrelated to any v1.8 shared-surface code: `nudge.py`/`checkins.py`/`test_v16_integration.py`'s `_run` helper are untouched by this pass.
  **Fix**: replaced the hardcoded date with `today = datetime.now(); clock = lambda: today.replace(hour=20, minute=0, second=0, microsecond=0)` in both tests — the nudge/check-in tick's "today" now always matches whatever real day `_run` actually logged on, so the tests stay green on any future run date rather than rotting again at the next midnight crossing (a more durable fix than re-pinning to today's specific date, which would only have deferred the same failure to tomorrow).

Neither fix touches production code or SPEC-v1.8.md's scope; both are documented here per Luna's "push back / flag, don't silently patch around" discipline, with root cause and reproduction evidence (file-ownership: I never edited `__init__.py`, `nudge.py`, `checkins.py`, or these two test functions' surrounding logic).
