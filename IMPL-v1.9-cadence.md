## How it works

`core/commands.dispatch` recognizes `/cadence <habit> <N>|off` (slash form, fully permissive like `/target`/`/remind`) and the Thai aliases `กี่ครั้งต่อสัปดาห์`/`ต่อสัปดาห์` (registry-anchored habit token + a valid value-tail shape, mirroring `_build_target_th_set_pattern`'s conservatism) and produces a `Command(kind="cadence", category=..., value_num=..., pref_value=...)`. `core/cadence.py:execute_cadence` resolves the habit against the caller's per-user registry, validates `1 <= N <= config.cadence.max_per_week`, and writes through `storage/db.py:set_cadence`/`clear_cadence` (upsert/delete on `habit_cadence`), auditing `cadence_set`/`cadence_clear`. The already-landed shared engine (`core/streaks.py`'s `_weekly_walk`, IMPL-v1.9-shared.md) picks up the new row on its very next read via `db.get_cadence` — no cache, no restart. `weekly_progress` reuses `streaks.day_qualifies` (the same qualification rule the engine's weekly walk uses) to compute "X of N this ISO week" without a second aggregation. `/addhabit ... | cadence=<N>w` is validated inside `habitdef.validate_and_normalize` (shape `^\d+w$`, range-checked against `cadence_max`) *before* any write happens, so a malformed value creates neither the habit nor a cadence row; on success, `execute_addhabit` writes the habit row, then the cadence row, in that order, each independently audited.

## Known limitations

- **AC9/AC10's "renderer wording" halves are integration-pass work, not a cadence-module gap.** `core/cadence.py` ships everything a renderer needs (`streak_unit` from the shared engine, `weekly_progress`, `cadence_status_line`) fully tested; SPEC-v1.9.md §11's file-ownership table does not list `review.py`/`dashboard.py`/`discoverability.py`/`main.py` under `cadence`'s owned files, and the integration-order section explicitly assigns "append each module's pure formatter into review.py/dashboard.py/discoverability.py" to the later, sequential integration step. I did not touch those files, per the parallel-build discipline (grace/pause/wrapped Lunas are editing concurrently; main.py routing is explicitly the later integration pass unless §11 assigns it to a track, and it doesn't here).
- **`/cadence <habit> <negative-number>` routes to the generic usage reply, not `cadence_invalid_value`**, via the slash-form matcher (a leading `-` isn't a recognized digit-only tail shape, unlike `/target`'s own value parser which explicitly accepts a leading `-` to reach its own downstream bounds check). The underlying bounds-check logic in `execute_cadence` does correctly reject a negative `value_num` when reached (verified directly in `test_out_of_range_n_returns_friendly_error_and_writes_nothing[n=-1]` by constructing the `Command` directly) — this is a minor, intentional shape-recognition choice, not a validation gap.
- **The second write in `/addhabit ... | cadence=<N>w` (habit row, then cadence row) is not wrapped in an explicit SQL transaction.** A malformed value is fully guarded (validated before any write, per AC8's own "creates neither"); a genuine DB error on the *second* write (after the habit row already committed) is fail-open — logged and reported via `addhabit_save_failed`, leaving the habit created without its cadence, mirroring this codebase's own established non-transactional, best-effort convention for every other multi-write command (e.g. `execute_addhabit`'s pre-existing `add_user_habit` + `habit_create` audit two-step). This is an extremely rare edge case (a mid-request DB failure) and not something any sibling module in this codebase handles more strictly.
- Full suite has 3 pre-existing failures in sibling-module-owned files (`test_commands.py`'s reserved-word table needs a `wrapped`-owned update; two `test_pause.py` tests) — see "Smoke test done" above. None touch `cadence`-owned code or tests.
