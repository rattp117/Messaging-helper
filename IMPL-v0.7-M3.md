## How it works

`compute_weekly_stats` walks `registry` once, calling the shared `Database.sum_value`/`count`/`count_true` generic aggregations per habit per day of the 7-day window ending on `end_date`, and returns one `HabitStats` per habit (numeric/duration get a `days: list[DayValue]` breakdown only when meaningful — numeric-with-goal for goal-adherence, always-empty for duration/text/boolean, which only need a rolled-up total/streak/count). `format_stats_summary` then walks `stats.habits` and, per habit, either calls the built-in's own v0.6.0 catalog entry with the same parameters (for `water`/`stretch`/`diary` — byte-identical by construction) or the type-generic `stats_generic_*` templates (for every other habit, keyed off `habit.type`). `run_weekly_review` is otherwise unchanged from v0.6.0: resolve the unprompted language, build the stats summary, ask the LLM for a narrative (falling back to the fixed fallback string on `None`/empty), and concatenate header + summary + narrative.

One deliberate design choice: the built-in `water` habit's goal is read from the legacy `config.reminders.water.goal_ml` field (via a small `_water_goal_ml` helper), **not** `registry.get("water").goal` — this exactly mirrors `main.py`'s own water confirmation branch (`goal = config.reminders.water.goal_ml`), which is the shared surface's own established pattern for "keep the built-in path byte-identical by reusing v0.6.0 code verbatim" (SPEC-v0.7.md §9 risk 2). All other habits (including a config-added numeric habit) read `habit.goal` from the registry, since they have no legacy config field to fall back to.

**Design choices not fully pinned by SPEC-v0.7.md §4 R16 / AC16** (documented so Vera/Archi can confirm intent):
1. **Numeric-without-goal review rendering**: SPEC-v0.7.md's i18n catalog (§5) only supplies `stats_generic_numeric_header`/`_line` (goal-adherence, needs a goal) and `stats_generic_numeric_total` (no goal reference). I render **only** the total/avg line for a goal-less numeric habit (no per-day header/lines, since there's no adherence to show), and both the per-day breakdown *and* the total/avg line for a numeric habit with a goal (matching how `water` renders today). This uses only catalog entries the shared surface already shipped — I did not (and could not, `core/i18n.py` is shared-owned) add a new template.
2. **Boolean "done-days" semantics**: AC16 says boolean gets "done-days"; there's no dedicated boolean catalog entry, so I reuse `stats_generic_count_summary` (same template text as `text`), with `count` = the number of distinct days `count_true(habit_id, day) > 0`, not the raw sum of truthy rows. Verified this collapses two same-day truthy logs to 1, not 2 (`test_generic_boolean_gets_done_day_count_not_raw_row_count`).
3. **Water's goal source**: kept reading `config.reminders.water.goal_ml` for the built-in `water` branch specifically (not `registry.get("water").goal`), mirroring `main.py`'s already-established pattern for the same habit — see "How it works" above.

None of these are gaps in AC15/AC16 coverage; they're implementation decisions where the spec under-constrains the exact rendering and I picked the option consistent with the shared surface's own conventions and the catalog entries actually available.

**Not implemented (per brief, correctly out of scope for M3):** the Garmin hydration cross-check TODO comment is kept verbatim, unimplemented (v1.0.0 per ROADMAP.md/SPEC.md §12, not this task). `main.py`'s `run_weekly_review` call site is still on the old 3-arg shape (untouched, per the "call-site flip happens at integration" instruction) — this is why no test that drives the review through `main.py`/`async_main` currently exercises the new registry-driven path; that's `test_multi_habit_integration.py`'s job (SPEC-v0.7.md §11, integration track), not M3's.
