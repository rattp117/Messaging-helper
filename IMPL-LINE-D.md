## How it works

`deploy/setup.sh` is the single entry point a fresh VPS runs once: it installs OS packages, creates an unprivileged `habitbot` system user, builds the venv, installs the app (`aiohttp` comes along as a base dependency already declared by the shared surface — no separate install step needed), seeds `.env`/`config.toml` from the two templates it never overwrites on a re-run, fixes `data/` ownership, and installs+enables the three systemd units without starting the main service (secrets aren't filled in yet at that point). The operator then does the LINE-console + Tailscale steps documented in `docs/DEPLOY-LINE.md`, edits `.env`/`config.toml`, and starts the service by hand — `deploy/setup.sh` deliberately never runs `tailscale funnel` or starts the bot itself, since both require state (an authenticated tailnet, filled-in secrets) the script can't safely assume. `config.toml.line` mirrors the repo's own `config.toml` in structure and habit catalog (same "thin channel swap" the spec argues for) but flips `[channel].type`/`[ollama].enabled` and fills `[line]`/`[digest]` — every other section is either an explicit, documented default or accepted-but-inert on this branch (noted inline where a flag has no live call site in no-LLM/LINE mode, e.g. `[outage].honest_reply`). The systemd units assume a standard `/opt/habit-assistant` install layout that `setup.sh` itself creates by cloning there — `WorkingDirectory` matters because `db_path`/`media_dir`/`backup.dir` in `config.py` are resolved relative to the process's cwd, not `REPO_ROOT` (verified: only `DEFAULT_CONFIG_PATH`/`DEFAULT_ENV_PATH` are `REPO_ROOT`-anchored).

## Maps to acceptance criteria

- **AC26** *(Given the systemd unit on Linux, When enabled and started, Then the app launches under the venv Python with `Restart=on-failure`, `EnvironmentFile=.env`, and a writable `data/`; no `.ps1`/Task-Scheduler logic is required)* → `deploy/habit-assistant-line.service` (R-D1) + `deploy/setup.sh` step 7 (`data/` chown, R-D4) + `tests/test_deploy_line.py::test_main_service_unit_has_required_directives`. The `.ps1`/`.plist` files are simply not referenced anywhere in Module D's deliverables — R-D1/D2 replace them outright for this branch, confirmed by the Windows-ism audit above (nothing in `src/` needs them either). Full `systemctl enable/start` execution itself is untestable outside a real systemd host (this dev box is Windows) — `test_systemd_analyze_when_available` runs the real verifier when the suite executes on Linux/the target VPS instead of asserting a fake pass here.
- **AC27** *(Given `docs/DEPLOY-LINE.md`, `config.toml.line`, `.env.example`, and `run.sh`, When followed, Then a fresh VPS reaches a running bot: venv → `pip install -e .` → Funnel exposing `bind_port` → webhook URL `/callback` registered in the LINE console → backup cron installed)* → `docs/DEPLOY-LINE.md` (the full runbook, all steps in order) + `deploy/setup.sh` (venv/install/backup-unit steps) + `config.toml.line`/`.env.line.example`/`.env.example` (the templates) + `deploy/run.sh`. Covered by `tests/test_deploy_line.py::test_config_toml_line_loads_clean`, `test_env_line_example_loads_via_load_secrets`, `test_deploy_line_doc_covers_the_required_runbook_sections`, `test_backup_cron_has_matching_schedule_and_flag`, `test_backup_timer_unit_fires_daily_and_is_installable`. The live end-to-end "fresh VPS → running bot" walk itself needs an actual Linux VPS + a real LINE channel + a real Tailscale tailnet — none of which exist in this dev environment — so this AC is verified at the **file/content-correctness level** (every artifact the runbook depends on is present, loads/parses/round-trips correctly, and the runbook's own text covers every required step), not by executing the runbook live. Flagging this explicitly for Vera/Archi: a live VPS dry-run is the one thing outside what a Windows dev-box CI run can prove.

## Known limitations

- **The full LINE gate (`pytest -m "not telegram_only and not llm_only"`) was not run to completion by this module** — Modules A/B/C were editing this same worktree concurrently while this build was in progress, so a full-suite run at that point would have mixed in-flight, unrelated changes and isn't Module D's gate to certify (Archi's explicit direction). This module's own verdict rests on the D-relevant foreground subset above (`test_deploy_line.py` + `test_config.py`, 73 passed/3 skipped) plus `test_deliverables.py` (8 passed, confirming the `.env.example` edit didn't regress). **The full LINE gate is deferred to the integration pass**, run once after A/B/C/D are all complete, per §11's own integration-order step 5.
- **No live VPS/Tailscale/LINE-console dry-run was possible in this environment** (Windows dev box, no Linux VPS, no real LINE channel provisioned). Every deliverable is verified for internal correctness (config loads, secrets round-trip, units have the right directives, scripts parse, PNG is valid) but the end-to-end "fresh box → running bot" flow in `docs/DEPLOY-LINE.md` has not been executed live. Recommend a real dry-run on an actual VPS before the first production LINE deploy, or an explicit Archi/user acceptance that the file-level verification here is sufficient for release.
- **`systemd-analyze verify` was not run** for the same reason (not available on Windows) — `tests/test_deploy_line.py` skips those 3 parametrized cases with an explicit reason string rather than omitting them, so the gap is visible in a test run rather than silent. The unit files were instead validated against a hand-written directive parser covering every field R-D1/R-D3 require.
- **`deploy/setup.sh` assumes a Debian/Ubuntu VPS** (`apt-get`) — it degrades gracefully (prints a note, doesn't fail) on any other distro but doesn't auto-install packages there. Matches the spec's own target ("small Linux VPS") without over-engineering for distros the user didn't ask for.
- **The rich-menu image is a placeholder**, per OQ3's own resolution — not a Luna decision to revisit; `assets/richmenu/README.md` documents exactly what a real design pass needs to know (size, button table, action type, font gotcha).
- **`config.toml.line`'s habit catalog mirrors the Telegram edition's three defaults** (water/stretch/diary) rather than a LINE-specific set — the spec names no different requirement, and this keeps the "thin channel swap" framing honest; trivially editable by the operator either way.
- No code in `src/` was touched by this module (correctly, per file ownership) — any src/ finding from the Windows-ism audit would have been *flagged* per R-D4's instruction, not fixed here, but there was nothing to flag.
