## How it works

Migration 009 adds one nullable column (dashboard opt-in state, mirroring `checkin_window`'s own no-backfill posture) and one new table (lifetime records, composite-keyed so "is this a new record?" is a single indexed lookup). `db.py` gets thin get/set/upsert methods with zero interpretation — `core/dashboard.py`/`core/records.py` (the parallel modules) own all the *meaning*. The channel layer's three new methods follow the exact same "concrete default degrades gracefully, `TelegramChannel` overrides with the real Bot API calls" pattern already established for `send_image`/`send_actionable`; `edit_message` is deliberately never-raising (every failure path — not-found, any other rejection, a transport error — maps to `False`) so `core/dashboard.py:refresh`'s self-heal logic (R-D4) has one honest boolean to branch on. `CommandKind` gained four skeleton entries (Literal declaration + field-reuse documentation only) so the four parallel modules (`dashboard`, `heatmap`, `insights`, `nudge`) can each add their own `_match_*` function and `dispatch()` branch without any of their diffs touching the same enum-declaration line.

## Regression found and fixed (pre-existing, not part of this pass's own scope)

While verifying "stays green," I discovered that `announce.announce_release` (wired into `main.py`'s real startup by my own earlier v1.5 integration pass) is now genuinely *active*: `src/habit_assistant/__init__.py:__version__` has been bumped to `"1.5.0"` as part of the actual v1.5.0 release (Archi's Phase 6.5 step, which happened after my v1.5 integration hand-off), and `RELEASE_NOTES["1.5.0"]` exists — so every test that drives a real `async_main()` startup with a seeded active user now unexpectedly receives an extra leading "what's new" message, none of which the affected test files' own scripts were written to expect (they predate the version bump becoming real). This is not a v1.6.0 regression and not something this pass introduced — confirmed via `git stash` against the clean v1.5.0-tagged commit, where the exact same failures reproduce with zero v1.6 changes applied.

**Root cause, concretely:** e.g. `tests/test_v12_integration.py::test_owner_autodetect_unaffected_when_no_lang_pref_ever_set` scripts two messages and asserts on `channel.sent_to(OWNER)[0]`/`[1]`; with the announce message now firing first, every subsequent index shifted by one, so the test's own confirmation-content assertions started comparing against the *previous* message instead of the one they meant to check.

**Fix:** each affected test file's shared `_run_async_main`/`_run`/`_run_job` harness now monkeypatches `main_module.__version__` (and, in `test_v15_integration.py`'s case, `access_module.__version__` too — Vera's own documented gotcha about the two separately-bound import sites) to an inert placeholder (`"0.0.0-test"`) that matches no `RELEASE_NOTES` entry, restoring every test's pre-bump-equivalent behavior. Files touched for this: `tests/test_v12_integration.py`, `tests/test_v13_integration.py`, `tests/test_history.py`, `tests/test_dnd_matrix.py`, `tests/test_streaks.py`, `tests/test_charts.py`, `tests/test_v15_integration.py`. One test (`test_v15_integration.py`'s own `test_current_pinned_version_has_no_release_note_and_announces_nothing_today`) existed *specifically* to lock in the pre-bump state — its own docstring explicitly predicted needing an update "the moment `__version__` is bumped... that's expected, not a bug"; renamed to `test_current_pinned_version_announces_to_active_users_today` and rewritten to assert the new (correct) post-bump behavior instead, using the real `__version__` constant read at test time (not a synthetic value) so it stays a genuine regression lock rather than a tautology.

I checked whether the coordinator's stated 2607 baseline was measured before or after this regression existed — it doesn't matter for this report either way: the fix is verified against the clean committed tree (pre-dating any of my v1.6 changes) and is unrelated to migration 009/channel methods/audit vocab/config/CommandKind — purely a test-harness staleness issue triggered by the version bump, of the same general *kind* (production behavior changed, test fixtures didn't track it) as the "500ml now bypasses the LLM" fixture-queue desync I found and fixed during the v1.5 integration pass.

## Known limitations

- **i18n.py skeleton sections were not added as bare comment markers**, unlike the v1.2/v1.5 precedent for `CommandKind`. Reasoning: `core/i18n.py`'s `CATALOG` is a single flat dict — a new module's key block can be appended anywhere in the file without colliding with another module's *insertion point*, as long as no two modules pick the literal same key name (already avoided by each module's copy using its own module-prefixed ids, e.g. `dashboard_*`/`heatmap_*`/`records_*`/`trends_*`/`nudge_*`, per SPEC-v1.6.md §6's own file-ownership table). The real collision risk `CommandKind`'s Literal declaration has (a single line/list every module would otherwise need to touch) doesn't apply the same way to a dict that's appended-to, not edited-in-place — so I judged bare section-marker comments unnecessary busywork here and instead left this note explaining the reasoning, so Archi/the four modules' own Lunas know this was a deliberate scope call, not an oversight. If any module's own Luna disagrees once actually landing keys, flag it back and I'll add the markers.
- **`config.toml`'s `[nudge]` section values match the code defaults exactly** (`threshold_pct = 80`, `time = "20:00"`) — self-documenting per this file's own established convention (every other section explicitly declares its defaults, e.g. `[snooze] default_minutes = 30`), not a behavior change.
- **The four `CommandKind` skeleton entries have no `_match_*` functions or `dispatch()` wiring** — by design, per §11's file-ownership table; each owning module lands its own matcher + one `dispatch()` branch. `tests/test_commands.py`'s new skeleton test documents and locks in this exact pre-module state so a future accidental early-match is caught.
- **The announce-harness regression fix (see above) is unrelated to v1.6.0's own SPEC** but was necessary to achieve a genuinely green suite; flagged prominently rather than buried, per the coordinator's own "stays green" requirement and this team's "report, don't silently absorb" discipline for anything outside a pass's literal scope.

## Contracts for the four parallel modules (`dashboard` / `heatmap` / `insights` / `nudge`)

- **`db.get_dashboard_msg_id(chat_id) -> str | None`** / **`db.set_dashboard_msg_id(chat_id, message_id: str | None) -> None`** — raw storage only, `None` = disabled. `core/dashboard.py:execute_dashboard`/`refresh` interpret it.
- **`db.get_records(user_id, habit_id=None) -> list[sqlite3.Row]`** / **`db.get_record(user_id, habit_id, record_type) -> float | None`** / **`db.upsert_record(user_id, habit_id, record_type, value, achieved_on) -> None`** — raw storage only, no comparison logic; `core/records.py:update_on_log` is the ONE place that decides whether a new value beats the stored one before calling `upsert_record`.
- **`Channel.send_and_pin(chat_id, text) -> str | None`** / **`edit_message(chat_id, message_id, text) -> bool`** / **`unpin(chat_id, message_id) -> None`** — `edit_message`'s `False` is the self-heal signal (R-D4); never raises. All three are already available on every existing channel/fake via the base-class defaults — no test fixture needs updating to keep working.
- **`CommandKind`**: `"dashboard"` reuses `Command.pref_value` (on/off/`None`=show, mirrors `"checkin"`); `"heatmap"`/`"records"`/`"trends"` reuse `Command.category` (habit filter) + `Command.limit` (only `"heatmap"` uses it, the weeks count — `"records"`/`"trends"` leave it `None`), mirroring `"history"`'s own tail grammar exactly.
- **`config.NudgeConfig`**: `threshold_pct: int = 80` (1–100, validated), `time: str = "20:00"` (HH:MM, validated), exposed as `Config.nudge`.
- **`core/audit.py` `Action`**: `"dashboard_set"`/`"dashboard_off"` are ready for `core/dashboard.py:execute_dashboard` to call `audit.record(db, actor=user_id, action="dashboard_set"|"dashboard_off", source="command", ...)` after each successful on/off write, mirroring `execute_checkin`'s own established pattern exactly.
- **`core/release_notes.py`**: `RELEASE_NOTES["1.6.0"]` already ships (EN+TH) — no module needs to touch this file.
