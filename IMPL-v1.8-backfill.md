## How it works

`extract_date` never imports a `HabitRegistry`, DB, channel, or LLM client — it only knows text and a `clock`. It tries every recognized EN/TH date-phrase body (§2.4: `yesterday`, `N days ago`, `(on|last) <weekday>`, `เมื่อวาน[นี้]`, `N วันที่แล้ว|วันก่อน`, `วัน<weekday>`) as a **whole leading clause first, then a whole trailing clause** of the stripped message — never a substring or mid-message match — resolves the matched phrase to a `date` against `clock().date()`, then bounds-checks it: future or older than `max_days_back` → `OutOfRange(reason=...)`; exactly today → `None` (R-B5's own "falls through unchanged"); otherwise `(residual_text, target_date)`. `main.py`'s integration step (not part of this pass) calls `extract_date` on the raw inbound text *before* `preparse.deterministic_parse`, feeds the residual through the existing extraction pipeline unchanged, and — on success — inserts the resulting `LogEntry` with `ts=backfill.backdated_ts(target_date)` and prefixes the normal confirmation with `backfill.confirmation_prefix(target_date, lang)`; on `OutOfRange`, it sends `backfill.bounds_error_text(...)` and writes nothing.

## Known limitations

- `main.py` is not wired yet (by design — that's the sequential integration seam SPEC-v1.8.md §11 assigns after all four modules land, not `backfill`'s own scope). `extract_date` is never called from `handle_inbound_message` in this pass.
- Anchoring is strict: a date phrase followed by *more* content past it (e.g. a colon-introduced continuation, `"diary 2 days ago: had a rough day"`) does **not** match, even though it starts with a genuine trailing-looking phrase — deliberately conservative per the module's own stated bias ("a missed backfill is recoverable; a misfiled log is not"). AC-C1's own phrase list uses the bare form (`"diary 2 days ago"`, no colon/continuation), which does match. Documented at length in `core/backfill.py`'s module docstring.
- Thai/full-width numeral normalization (`๓`, `３` → `3`) is scoped to only the digit run inside a recognized `N วันที่แล้ว|วันก่อน` phrase — it does not touch the residual text, so it cannot change how `preparse`/the LLM interprets the rest of the message. No such normalizer exists elsewhere in this codebase to reuse (checked: `core/units.py:VALUE_RE` is ASCII-digit-only), so this is a new, self-contained helper local to this module.
- The bilingual weekday/month abbreviation tables (`Mon`/`Tue`.../`จ.`/`อ.`...) are new to this codebase — `core/heatmap.py`'s own chart deliberately stayed English-only/numeric for exactly this reason (per its module docstring), but §3.4's confirmation format requires real bilingual day names, so this module built its own small tables rather than reaching for `strftime`'s locale-dependent output (which this codebase never relies on elsewhere).
- `resolve_days_back` is provided as a ready-made helper for `main.py`'s eventual wiring of the LLM's optional `date_offset` field (R-B5: "subject to the same bounds") — it is unit-tested here but not yet called from anywhere, since the LLM extraction path itself is out of this module's scope.
