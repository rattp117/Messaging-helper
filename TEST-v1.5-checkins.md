### What `test_checkins_gaps.py` adds beyond Luna's suite
- **Opt-in holds absolutely**: a full simulated day (24h × 4 quarter-hours) across 5 active users, nobody enabled → zero sends; explicit `checkin_window IS NULL` check per user (pre-v1.5-shaped, no-backfill).
- **Window semantics**: silence at `:30` (not just `:01`/`:59`); midnight-crossing windows (`22:00-06:00` and `20:00-08:00`) proven to **never fire at any hour** — confirms IMPL-v1.5-checkins.md's own documented "Known limitation #3" (R-K2's plain `start ≤ HH:00 ≤ end` string compare has no wraparound, unlike `/quiet`) is exactly what's implemented, not a surprise; degenerate `08:00-08:00` fires only at that one hour.
- **`/checkin` adversarial shapes**: `"maybe"`, `"8-20"`, an en-dash window (`08:00–20:00`), `"25:00-20:00"` → usage reply, no write. Extra Thai corpus: mai-yamok (`เช็คอินๆ`), polite particles (`เช็คอิน ค่ะ`), a valid-prefix-plus-trailing-particle (`เช็คอิน on ครับ`), and a newline mid-message — all correctly fall through to `None`. Extra `/dnd` Thai adversarial cases too.
- **Collision sweep**: all 16 other `CommandKind`s' canonical triggers still reach their own kind (never shadowed by `_match_checkin`/`_match_dnd`), and `/checkin`/`เช็คอิน`/`/dnd`/`งดรบกวน` reliably reach theirs (never shadowed by an earlier matcher) — both directions, 20 parametrized cases.
- **R-K8 literal-window immunity**: `/checkin on` stores `"08:00-20:00"` literally; changing `config.checkin.window` afterward to `"06:00-22:00"` does **not** shift the enabled user — proven behaviorally (fires at 08:00, stays silent at 07:00 even though 07:00 is inside the *new* config default).
- **Content correctness**: mixed goal/goal-less habits (real `water`+`stretch`+`diary` registry) — skip uses only the goal-bearing set; target-override (`db.set_target`) vs config default, both directions (override lower → skips when config default wouldn't; override higher → stays unmet when config default would call it met) — manually spot-verified with a standalone script that the test genuinely discriminates real behavior, not a vacuous pass; live totals across two ticks an hour apart reflect the day-to-date total at each firing moment.
- **Suppression interplay**: a per-habit reminder (`reminders.run_due_reminders`) and the check-in tick both fire independently for the same user in the same minute (2 separate sends) — no unintended collision/dedupe between the two ticks. `/dnd`'s audit row (`db.recent_audit`) is byte-for-byte the same shape (`action="quiet_set"/"quiet_off"`, same `source="command"`, same stringified `new_value`) as an equivalent `/quiet` write — there is no `"dnd_set"` in the closed `audit.Action` vocabulary at all, confirming true indistinguishability downstream, not just at storage.
- **Isolation stress**: 4 users in 4 different states (enabled/no-DND, enabled/always-DND, never-enabled, enabled/out-of-window) plus OWNER/MEMBER, one shared tick → exactly the one eligible user is sent to.

## Out-of-scope finding (for Archi/announce track awareness)
`tests/test_announce_gaps.py::test_concurrent_overlapping_calls_send_at_most_once_per_user` fails deterministically: `announce.announce_release` has a real TOCTOU race between its "already announced?" read and its mark-on-success write — two concurrent calls (`asyncio.gather`) can both pass the read-check before either writes, so a user receives 2 sends instead of 1. This is entirely inside the `announce` module (not `checkins`'s file ownership, not touched by this pass) and was already present before I started this session. When run as part of the full suite, this test's concurrency also has an order-dependent side effect that intermittently fails 4 tests in `tests/test_backup.py` (confirmed: `test_backup.py` passes 17/17 clean in isolation, and the full suite is 100% clean when `test_announce_gaps.py` is excluded). Recommend routing this back to the `announce` module's own Luna↔Vera loop — not a reason to hold up `checkins`.

## Environment note (resolved during this pass, not a code defect)
Partway through this test pass, the shared `.venv` (which lives inside a OneDrive-synced folder) suffered active, repeated corruption from OneDrive's Files-On-Demand sync engine — confirmed via a genuine Windows Cloud-Files error (`os error 396`, "incompatible hardlinks") during a `uv pip install`, plus dozens of third-party packages (pytest, pydantic, httpx, numpy, matplotlib, anyio, tzdata, etc.) intermittently losing their source files in real time. This was unrelated to `checkins`'s own code and is a pre-existing infrastructure risk (running a Python venv inside a OneDrive-synced tree is a known-fragile pattern) — flagging for Archi: consider moving `.venv` outside the OneDrive sync root, or excluding it via OneDrive folder exclusion, to prevent this recurring in future sessions. I repaired the environment using only non-destructive means (`uv pip install --no-deps` and same-version cache-to-target file copies for missing files, never touching `data\habits.db`, never restarting the live Task-Scheduler-managed service, never using `uv run`/`uv sync`) and re-verified every result reported above after the repair, twice, for stability.
