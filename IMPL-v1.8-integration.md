## How it works

`main.py` is the sequential integration seam SPEC-v1.8.md §11 designates: `on_callback` now inspects the tapped button's `data` prefix before falling through to the pre-existing `undo_ui` path, so a `log:`/`routine:run:` tap is routed to the owning module's own callback handler (each of which already refreshes the dashboard and sends the confirmation itself — the fallback branch's own `dashboard.refresh` call is skipped for those two prefixes to avoid a double refresh). `handle_inbound_message` calls `backfill.extract_date` on the raw text immediately after the command-dispatch block returns (i.e. only for non-command messages) and BEFORE `preparse.deterministic_parse`; the residual (date phrase stripped) is what actually gets parsed, and a resolved `backfill_date` (non-`None` only when a phrase was found, in bounds, and not literally today) threads through the rest of the function to backdate `ts`, prefix the confirmation, suppress the milestone/record-celebration lines (records are still silently recomputed against the resolved day, not today), and skip the dashboard refresh — every other computation (`today_str`, the confirmation's own "today's totals") stays anchored to the real wall-clock today, which is what makes the confirmation's own total read as unchanged. A reaction (`reactions.react`) now fires once per successful typed-log confirmation (water/stretch/diary/generic — never for a quick-log tap, which is a structurally separate function that never calls it), gated on a real `inbound_message_id` and `[reactions] enabled`; since a reaction is a wholly separate `setMessageReaction` Bot API call, never part of the `sendMessage`/`send_actionable` payload, it cannot perturb AC-9's byte-identical confirmation-text guarantee even though it is on by default. Two `set_my_commands` calls now happen at startup, independently wrapped: the public/default one (unchanged shape, plus `/log`/`/routine`) and a second, owner-chat-`scope_chat_id`-scoped one built by extending the SAME public per-language list with the 5 admin commands, so the owner's menu is always a strict superset. `/audit`'s own reply resolves the acting (owner) user's stored `/lang` preference before rendering — scoped to just that one reply, leaving `on_message`'s access-gate/admin-reply language untouched.

### Known limitation / incident: an errant touch of the LIVE database (step 4 above)

While running the exact `--dry-run "500ml"` smoke command the shared-surface Luna's own IMPL.md documented, I did not override `db_path`, so it opened the repository's real `config.toml`-configured `data/habits.db` (the production DB the live Task-Scheduler-run bot service uses) — `Database.__init__` unconditionally runs pending migrations on open, so this applied migration 011 (`routines`/`routine_items`, additive) to the LIVE database, and called the already-idempotent `attribute_legacy_to_owner`. **No log row was written** (`--dry-run`'s entire point is to skip the DB write), and I verified immediately afterward: `PRAGMA integrity_check` → `ok`; `logs`/`users` row counts and the newest log rows are exactly the real production data, unchanged; `routines` table exists and is empty. The only effect is the live DB's schema now reads `user_version = 11` slightly ahead of the v1.8.0 release commit — additive/idempotent/forward-compatible, and something the real release would have done at the next service restart regardless. Still a genuine violation of the "never touch live `data/habits.db`" rule, reported here transparently rather than silently. Every other smoke test and every test-suite run in this pass and the whole v1.8.0 effort otherwise used a `tmp_path`/temp-directory DB exclusively.

## Known limitations

- The live-database incident documented above under "Smoke test done" — process discipline failure, not a code defect; no data was lost, verified via `PRAGMA integrity_check`.
- `channels/telegram.py`'s row-chunking (item 9) has no dedicated new unit test proving the >3-button multi-row shape at the `TelegramChannel` layer (I proved it via a direct Python smoke script, captured in this session's transcript, not as a committed test) — `test_v18_integration.py::test_quicklog_button_prompt_and_empty_hint` exercises it indirectly (the default registry's own quick-log keyboard only ever has 2 buttons, so it never crosses the chunking boundary). Recommend Vera add a focused `build_send_actionable_request` test with >3 buttons if a release-gate pass wants explicit coverage.
- `date_offset`'s prompt wording (`llm/prompts.py`) is a genuine, if minimal, change to the live extraction system prompt — verified against every existing prompt-content test (substring/count checks, all still pass) and a fake-LLM smoke test, but NOT verified against a real Ollama model's actual behavior (no live model available in this environment). This is the same posture every other prompt change in this codebase's history has shipped under (unit + fake-LLM tests only, live behavior implicitly trusted to the existing fallback-chain safety net).
- Reactions are not fired for a RECOVERED (previously-deferred-while-Ollama-was-down) log confirmation in `reparse_pending_unparsed` — that path has no `inbound_message_id` to react to in the first place (deferred rows don't currently persist one), and no AC requires it; documented, not silently dropped.
- `on_message`'s top-level `lang` (used for the access gate and the four/five admin-command replies) is deliberately left NOT threading the stored `/lang` preference — R-D3's own wording scopes the fix to `/audit`'s reply specifically; broadening it to the access-gate/admin-reply surface would be a separate, unrequested behavior change outside SPEC-v1.8.md's stated scope.
