## How it works

`resolve_reply_value` is a pure function: given the reply text and the `Habit` that `core/reminders.py:ReminderState.habit_for_reply` (shared surface) already resolved the reminder's message id to, it returns a value only for the two conservative cases R14 defines, `None` for everything else — the integration seam (`core/routing.py`, not part of this module) is expected to call `habit_for_reply` first and only invoke `resolve_reply_value` when that resolves, then fall through to the normal preparse/LLM path on any `None`. `build_guide_text` is a fixed, config-independent bilingual string built the same way `build_help_text` is, backed by 5 new `guide_*` catalog entries. `outage_honest_reply` is a new bilingual catalog entry (no wrapper function — mirrors how `deferred_ack`/`clarifying_question` are plain `i18n.t()` lookups today) that the integration seam will select instead of `deferred_ack` when `config.outage.honest_reply` is true. The two sanctioned EN-string fixes changed `confirm_numeric_goal`/`confirm_numeric_nogoal`'s English templates to include `{label}` (matching `confirm_duration`'s pre-existing EN word order: value, unit, label, "logged") so a custom numeric habit's English confirmation names the habit, exactly like the Thai variant already does.

## Known limitations

- `outage_honest_reply` is not truncated/capped for a very long saved message — matches SPEC-v1.10.md §3.4's own worked example (no truncation shown) and this release's `closure_*` (M1) precedent, neither of which caps the quoted raw text. Flagging for Archi/Vera: in the theoretical case of a raw message close to Telegram's own ~4096-char inbound limit, the wrapped outage message could exceed the 4096 outbound `sendMessage` limit. Out of R15's stated scope (no AC calls for capping here); `tests/test_outage_honesty.py::test_outage_honest_reply_handles_a_long_raw_message_without_crashing` only guards against a crash, not a length bound.
- `build_guide_text` accepts but does not read `config` — there is no config-driven content in R16's scope today; kept for interface parity with SPEC-v1.10.md §5's literal signature and to allow a future config-driven line without a signature change.
- Full end-to-end wiring (reply-attribution branch in `handle_inbound_message`, outage-message dispatch in the deferral branch, `/guide` routing + menu registration) is the sequential integration seam's responsibility per SPEC-v1.10.md §11 — this module's tests deliberately stop at the pure-function/catalog-copy boundary and do not simulate `core/routing.py`'s real branches.

## Sanctioned EN-string change — verification and scope (Archi's item "b")

Per dispatch: *"confirm_numeric_goal and confirm_duration EN templates omit {label} while TH includes it"*. I read `src/habit_assistant/core/i18n.py` and `src/habit_assistant/core/confirmation.py` directly before touching anything, per the explicit instruction to verify which keys are actually affected:

- `confirm_numeric_goal` — EN omitted `{label}`, TH had it → **broken, fixed**.
- `confirm_numeric_nogoal` — EN omitted `{label}`, TH had it → **also broken** (not named in the dispatch, but the exact same bug — same root cause, same fix, same rationale "a custom habit's English confirmation never named it"). Fixed alongside the other two for consistency; flagging the discrepancy here in case Archi wants to confirm this extra fix.
- `confirm_duration` — EN **already** included `{label}` (`"✅ {value:g} {unit} {label} logged — {ordinal} today"`), matching TH's information content. **Not broken, not touched.** The dispatch's mention of `confirm_duration` appears to be based on the documentor's summary rather than the current code; I verified this directly and left it unchanged (its own EN word order — value, unit, label, "logged" — is in fact what I used as the template for fixing the other two, for in-app consistency).
- `confirm_text`/`confirm_boolean` — both languages already include `{label}` → not in scope, not touched.
- Base-habit dedicated keys (`water_confirmation`, `stretch_confirmation`, `diary_confirmation`) → untouched, as instructed (logging water/stretch/diary never needs a label — the confirmation IS the habit).
- `edit_updated_numeric`/`undo_removed_numeric` (and their duration/boolean siblings) → both EN and TH already agree (either both omit `{label}` or both use `{description}`, which already embeds the label via `describe_log_*`) → no EN/TH divergence, out of scope, not touched.

**quicklog parity**: `core/quicklog.py` imports `confirmation.confirmation_text` directly (no independent copy of the templates) — confirmed by grep before making the change. The fix is therefore automatically shared by both the typed-log and `/log`-button paths; no `quicklog.py` edit was needed and no parity test broke.
