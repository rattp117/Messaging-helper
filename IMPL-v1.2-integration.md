## How it works

`main.py`'s `on_message` closure is now the actual seam SPEC-v1.2.md §11 describes: it resolves the acting chat's reply language, calls `access.handle_gate` (which is a no-op — returns `True` immediately — for `owner`/`active`, and otherwise sends the onboarding/refusal reply itself and returns `False`, at which point `on_message` returns without ever touching `logs` or the LLM); for a proceeding chat, it dispatches once to check for the five owner-only/onboarding command kinds and routes those to `access.execute_admin` (which needs `owner_chat_id`, not a parameter of `handle_inbound_message`); everything else falls through to `handle_inbound_message` exactly as before, except that function now also recognizes `lang`/`quiet`/`remind` internally (mirroring `target`/`help`/`habits`'s own recognize-shape/execute split) and resolves the acting user's own stored `/lang` preference into every reply's language, not just the `/lang` confirmation itself. `on_callback` gained a matching, lighter check — `access.classify` (not the full onboarding `handle_gate`, since a button tap isn't a message to onboard from) — so a stale button from a since-blocked or never-approved chat can't execute an undo. `TelegramChannel.run()` now extracts the sender's `first_name` from each update and passes it as `on_message`'s optional third argument, which `main.py` threads straight into `handle_gate`'s `display_name` parameter so `access_request`/`/users` show a name instead of a bare chat id. The five call sites SPEC-v1.2.md's punch list named for per-user language threading (`main.py:handle_inbound_message`, `reparse_pending_unparsed`, `weekly_review_job`, `daily_summary_job`, and `core/reminders.py:run_due_reminders`) each now resolve `i18n.resolve_reply_language`/`resolve_unprompted_language` with a `user_pref=` argument sourced from a small, duplicated-per-file, fail-open helper (`db.get_user(user_id)`, defaulting to `"auto"` on a missing row or a DB error) — matching `core/access.py`'s own pre-existing `_resolve_unprompted_language_for` pattern rather than introducing a new cross-module dependency.

## Known limitations

- **`--dry-run`/a direct `handle_inbound_message` call still can't exercise `access`'s five admin/onboarding kinds.** `execute_admin` needs `owner_chat_id`, which isn't one of `handle_inbound_message`'s parameters, and `access.handle_gate` itself was never wired into that function (by design — the gate has to run before dispatch, and `--dry-run`/tests bypass `on_message` entirely). A direct call with `/approve 123`-shaped text now hits a **documented, safe no-op** (this pass's own addition, beyond the literal punch list — see "Deviations" below) instead of the pre-existing silent-edit-fallthrough risk. Fully fixing this for `--dry-run` would mean threading `owner_chat_id`/a gate call into that CLI path too, which the coordinator's punch list didn't ask for and which the underlying `access`/`preferences`/`schedules` IMPL docs never claimed `--dry-run` support for either — flagging as a possible fast-follow, not a regression.
- **The live-Ollama smoke check (item 4 above) didn't actually complete a live extraction** due to a sandbox-specific network-namespace limitation (see the note in "Smoke test done") — `curl` reached `mac-mini:11434` from this session's shell but this sandboxed Python process's `httpx` client could not. The 1307-test mocked-Ollama suite plus the fail-closed behavior observed in the smoke script are the actual evidence base for this release; a genuinely live round-trip (like `IMPL-v1.1-integration.md`'s own item 4) could not be reproduced in this environment. Worth re-attempting from an unsandboxed shell if live confidence is specifically wanted.
- **`/help`'s three new lines (`/lang`, `/quiet`, `/remind`) are unconditional**, unlike the two lines just above them (`help_quiet_hours_on/off`, which reflect the live global config). This matches every user's ability to always run all three regardless of the global config's own defaults — not an oversight, a deliberate difference in shape from the neighboring lines.

## Deviations from the literal punch list (all additive, documented as directed)

1. **A safety-net no-op for the five `access`-owned command kinds inside `handle_inbound_message`**, not explicitly requested by the punch list. While wiring the routing, I found that any of those five kinds reaching `handle_inbound_message` directly (bypassing `on_message`, e.g. a future `--dry-run` caller or a test) would silently fall through to the generic `command.kind == "undo" else _execute_edit(...)` branch — and because an access `Command`'s `category`/`value_num` are both `None`, `_execute_edit` would call `db.update_value(row["id"], value_num=None)` on the user's most recent log of ANY category, **nulling its value**. This is a real (if narrow-exposure) data-corruption risk, not a hypothetical, discovered while implementing the literal ask ("route access/admin kinds to `access.execute_admin`") — fixing it is directly adjacent to that work, so I fixed it rather than filing it separately. Documented in `handle_inbound_message`'s own docstring and the code comment at the guard.
2. **The exact command-menu inclusion list** (which of the 8 new-since-v1.1 commands join the public `setMyCommands` menu) wasn't specified by SPEC-v1.2.md itself (confirmed by grep — no §2.3/§5 mention of menu content). Per the coordinator's own instruction ("follow spec, document the call"), I included `/start` (available to any user, R-A5, not owner-only) and `/lang`/`/quiet`/`/remind` (genuinely user-facing), and excluded the four true admin commands (`/approve`/`/block`/`/users`/`/invite`, R-A4, owner-only) — since `setMyCommands` is global (R-C1), listing them would advertise owner-only capability to every ordinary member. Recorded in `main.py`'s own `START_/LANG_/QUIET_/REMIND_COMMAND_DESCRIPTIONS` docstring.
