## How it works

`handle_inbound_message` now routes `"dashboard"`/`"heatmap"`/`"records"`/`"trends"` alongside the existing deterministic, LLM-free commands (`"checkin"`/`"history"`/`"help"`), each before the health-monitor deferral check. The log-confirmation block computes `record_suffix` (via `records.update_on_log`, already fail-open internally) right after the pre-existing `milestone_suffix` computation and concatenates the two (`milestone_suffix + record_suffix`) into every one of the four confirmation sends; each send is immediately followed by `await dashboard.refresh(...)`, always AFTER the `channel.send_actionable`/`channel.send` call that carries the confirmation, never before — the same ordering discipline is applied to undo (both paths), edit, target changes, and the deferred-message recovery path. `dashboard.refresh` and `records.update_on_log` are both fail-open by their own construction (whole-body `try`), so none of these integration call sites need an extra wrapper. The weekly review's `core/review.py:run_weekly_review` appends `trends.review_block`'s output last, pinned to the review's own `end_date` rather than the real wall clock. Two new scheduler jobs run alongside the pre-existing `reminder_tick`/`checkin_tick`: `nudge_tick` (minutely, mirrors `checkin_tick`'s own internal-guard shape) and `dashboard_day_rollover_job` (a native once-daily `CronTrigger`, mirroring `daily_summary_job`/`weekly_review_job`'s own established pattern more closely than `core/dashboard.py`'s own suggested minutely-tick wiring note — see Known Limitations for the reasoning).

## Regression root-cause note (for Vera's awareness)

Wiring `records.update_on_log` into the live confirmation path surfaced the same *class* of pre-existing test staleness discovered during the v1.5 integration pass (there: "500ml" bypassing the LLM once `deterministic_parse` landed; here: a fresh user+habit's first log now silently seeding a `best_day`/`best_week`/`longest_streak` baseline that a later same-day/same-streak log can genuinely, correctly break). Four pre-existing tests exercised exactly this shape (two same-day logs for a fresh habit, or a real multi-day streak) and needed a `db.upsert_record(...)` pre-seed to stay focused on what they actually test (confirmation-text formatting, milestone sequencing) rather than getting entangled with the new, unrelated celebration line. A fifth test (`test_garmin.py`'s own v0.10.0 byte-identical pin) needed updating for a different, expected reason: `trends.review_block` is unconditionally non-empty (always at least a header line), unlike Garmin's genuinely-empty-when-unconfigured contract, so "byte-identical to the whole v0.10.0 output" is no longer achievable by construction — the test now pins the v0.10.0 shape as an exact prefix instead. Two more (menu exact-set tests) were the expected mechanical "the public menu grew" bump, same pattern as every prior version's own menu additions.

## Known limitations

- **Day-rollover uses a native daily `CronTrigger(hour=0, minute=0, ...)` instead of `core/dashboard.py`'s own suggested "minutely tick + `hhmm == "00:00"` guard" wiring note.** Reasoning: day-rollover is a single fixed daily instant (exactly like `daily_summary_job`/`weekly_review_job`, both of which already use this exact native-cron pattern), unlike `checkin_tick`/`nudge_tick`, whose minutely-tick-with-guard shape exists specifically because those functions evaluate a per-user WINDOW that can span many hours, not a single instant. This is a deliberate, documented design call (not a silent deviation) — functionally identical (fires exactly once at 00:00 daily, same `coalesce`/`max_instances`/`misfire_grace_time` safety), one fewer per-minute wake-up, and more consistent with this codebase's own two existing single-daily-instant jobs. Flagging per the coordinator's own "push back with a concrete alternative, don't silently deviate" instruction — happy to switch to the minutely-guard shape if there's a reason (e.g. future per-user-configurable rollover time) I'm not seeing.
- **`records.update_on_log` is NOT wired into `reparse_pending_unparsed`'s recovery path** (dashboard refresh IS, per that module's own explicit "R-D5 explicitly calls out the recovery case" instruction). Neither the insights module's own IMPL nor SPEC-v1.6.md's R-R2 text ("in the same place the milestone check runs") extends to this path — `reparse_pending_unparsed` has never computed `milestone_suffix` either (a pre-existing, pre-v1.6 asymmetry between the live and recovery confirmation paths), so extending records there alone, without also retrofitting milestones, would be new unrequested scope. Flagged for Archi/Sophia if a delayed/recovered log should also be able to break a record — currently it can seed/update `best_day`/`best_week`'s underlying totals implicitly (since those are recomputed live from `logs` whenever `update_on_log` next runs for that habit+user, e.g. on the next live log), just not celebrate at the moment of recovery itself.
- **`help_dashboard_cmd` copy is my own drafting** (mirroring `dashboard_usage`'s established tone), since `core/dashboard.py`'s own module explicitly flagged not shipping one. No AC depends on its exact wording.
- **Testing note**: two of `test_v16_integration.py`'s 18 tests needed a fix during authoring, both caught by the standard "run it, don't just write it" discipline: (1) the self-heal test initially reused the same clock/data as the preceding "on" message, so `dashboard.refresh`'s own R-D3 unchanged-render cache skipped the edit attempt entirely before ever reaching the forced failure — fixed by clearing `dashboard._last_rendered` for that user before the direct `refresh` call; (2) the registry-generic test's synthetic habit used unit `"reps"` but the scripted log message said `"20 pushups"` (the habit's *label*, not its configured *unit* token) — deterministic_parse/dispatch correctly failed to match it, so nothing was ever logged; fixed by changing the message to `"20 reps"`.
