## Design choice: raw `httpx` over `python-telegram-bot`

Went with raw `httpx` for `TelegramChannel`, per SPEC §3's "your call, justify briefly" and the environment brief's minimal-dependency steer. One HTTP client library (`httpx.AsyncClient`) serves both `TelegramChannel` (long-poll `getUpdates` + `sendMessage`) and `OllamaClient` (`/api/chat`), so there's no second async HTTP stack to reason about, and both channels/LLM clients accept an injected `httpx.AsyncClient` for testing (mock transports) without pulling in `python-telegram-bot`'s update/dispatcher machinery, which is more than this MVP's single linear inbound loop needs.

## How it works

1. **Startup** (`main.py:async_main`): loads `config.toml` (`Config`, always succeeds — falls back to defaults) and, for real runs, `.env` (`Secrets` — raises `ConfigError` with a clear message if the token/chat-id are missing, caught and printed to stderr with exit 1). `--seed` and `--dry-run` skip the secrets load entirely since they don't need Telegram.
2. **Inbound message flow**: `TelegramChannel.run` long-polls `getUpdates` and calls `on_message(text)` for every inbound message (never conditioned on whether a reminder preceded it, per SPEC §3). `on_message` wraps `handle_inbound_message`, which calls `core.parser.parse_message` → `OllamaClient.chat_json` (POST `/api/chat`, `stream: false`, `format: <json schema>`, `think: false`) → `strip_think_and_prose` → `json.loads` → schema/enum validation. Any failure at any step (HTTP error, malformed JSON, invalid enum, wrong types) returns `ExtractionResult.unknown()` — the parser never raises, so `TelegramChannel.run`'s per-message try/except is a second line of defense, not the primary one.
3. **Write + confirm**: for `water`/`stretch`/`diary`, `handle_inbound_message` writes one `logs` row (`storage/db.py`) then sends the confirmation text (running total/goal/%, ordinal stretch count, or an LLM-generated one-line reflection for diary) via the injected `Channel`. For `unknown`, it sends the clarifying question and writes no row.
4. **Reminders + weekly review**: `core/reminders.py:schedule_reminders` registers one `AsyncIOScheduler` cron job per configured time (10 jobs with defaults: 6 water + 2 stretch + 1 diary), plus `main.py` registers the weekly-review job directly (Sunday 20:00 by default). The review job calls `core/review.py:run_weekly_review`, which aggregates 7 days of `logs` via `Database`, formats a factual stats block, asks Qwen for a short narrative (`chat_text`, falls back to the plain stats block if the LLM call fails), and sends the combined text.
5. **Channel seam**: `channels/base.py:Channel` is the only channel-related import allowed in `core/`, `storage/`, or `main.py`'s type hints — `main.py` is the sole place that constructs a concrete `TelegramChannel`. Verified with `grep -i "import.*(telegram|line)"` across `core/` and `storage/`: no matches.

## Known limitations

- **MLX backend doesn't enforce the `format` JSON schema** (see finding above). Mitigated with few-shot examples + strict server-side validation that fails closed, but this is a soft mitigation, not a guarantee — an adversarial or unusual message could still get an off-schema response from this specific model/backend combination that happens to *coincidentally* match the schema shape with wrong semantic values (e.g. a bogus `water_ml` that isn't obviously wrong to the validator). Correctness of *values* (not just shape) depends on the model actually following instructions; this is inherent to LLM extraction and true of any model, not unique to this bug. If the user finds live accuracy insufficient, switching `[ollama].model` in `config.toml` to a GGUF model (e.g. `qwen3:8b`, confirmed schema-conformant on this server) is a one-line config change, no code change.
- **LINE channel**: stub only, per SPEC §12/§8 — `channels/line.py` raises `NotImplementedError` and documents why (needs a public webhook, unlike Telegram's long-poll).
- **Garmin CSV import**: not implemented; `TODO` left in `core/review.py` per SPEC §12.
- **No real Telegram token available this session** — `TelegramChannel.send`/`run` are verified via request construction (`build_send_request`) and one live round-trip to `api.telegram.org` that correctly reached the server and got `401 Unauthorized` from a deliberately fake token (proves the HTTP path is correct; the 401 itself is expected, not a bug). Full send/receive against a real bot needs the user's real `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` in `.env` — `.env` was intentionally left absent at handoff (gitignored either way) so the "missing token" startup error (AC1) is what a fresh clone actually experiences.
- **DB concurrency**: `Database` uses one `sqlite3.Connection` on the event-loop thread, no thread pool — correct for this app's single-process, single-consumer-of-DB shape (inbound loop and scheduler jobs all run on the same asyncio loop, so calls are naturally serialized), but would need revisiting if a future feature added true multi-threading.
- **Windows-primary changes not yet reflected in `SPEC.md`/`PROGRESS.md`**: the coordinator's scope update (Windows as primary host, Ollama at `http://mac-mini:11434`, model `qwen3.5:9b-mlx`) was applied to `config.toml`, `README.md`, and `start-assistant.ps1`, but `SPEC.md` itself (owned by Sophia/Archi) still describes the original Mac-Mini-primary plan. Implements `ROADMAP.md` §"v0.2.0" on top of the released v0.1.0. Scope: a startup schema-conformance probe, an ordered model fallback chain in `chat_json`, and a confidence-threshold gate that turns a low-confidence-but-schema-valid extraction into a clarifying question. No new dependencies.

## How it works

`OllamaClient` now holds an ordered list of models (`self._models`). `chat_json` walks that list, POSTing to each in turn via the shared `_post()` helper; a model's response is accepted the moment `_has_recognizable_category()` (a lightweight "does the parsed JSON have a `category` matching the schema's enum?" check) passes — the first model that clears this gate wins, and if none do, `chat_json` returns `None` so `parse_message` fails closed to `unknown`, exactly as before. `core/parser.py._validate` still owns all business-rule validation (value ranges, required companion fields) and now additionally demotes an otherwise-valid result to `unknown` when its (genuinely present, numeric) `confidence` is below `config.ollama.confidence_threshold`. `probe_schema_support()` is a separate, stricter, purely-informational path: at real-run startup it sends one fixed probe message to every configured model and logs whether the response's JSON keys are *exactly* the 5 required schema keys — this never influences runtime routing, it only tells the operator (via `logger.info`/`logger.warning`) which models honor `format`.

## How it works

`storage/migrations.py:run_migrations` is the single place schema evolution happens: it reads `PRAGMA user_version`, and for every migration function above that index runs it inside an explicit transaction (`conn.isolation_level = None` for the duration, so `BEGIN`/`COMMIT`/`ROLLBACK` are under this module's control rather than sqlite3's implicit DML-only transaction heuristics — needed because migrations are DDL, which sqlite3's default isolation mode doesn't auto-wrap), then stamps `PRAGMA user_version` to match, and commits — schema change and version stamp succeed or fail together. `storage/db.py:Database.__init__` calls this once per process, right after opening the connection and setting WAL, so every code path that ever constructs a `Database` (the real bot, `--seed`, `--dry-run`, `--migrate`, tests) transparently gets migrated forward; a DB already at the latest version is untouched (`from_version == to_version`, nothing executes). `core/backup.py:backup()` opens a *second* `sqlite3.Connection` to the same file and uses `source.backup(dest)` — SQLite's C-level online backup API — which correctly reads committed pages plus anything still resident in the WAL, so a backup taken while the live process holds its own WAL connection open still captures the latest writes (verified live in the smoke test below, not just asserted). `restore()` never mutates `db_path` until `_validate_sqlite_file(archive_path)` has fully passed (readable as SQLite, passes `integrity_check`, has the `logs` table) — only then does it take an automatic backup of the current DB and atomically `Path.replace()` a copy of the archive over `db_path`, clearing any stale `-wal`/`-shm` sidecars left over from the DB it replaced. `main.py`'s three new CLI branches sit in the same "doesn't need Telegram" block as `--seed`/`--dry-run`, before `load_secrets()` is ever called.

## Known limitations

- **Blocking `pyproject.toml` BOM bug fixed, unrelated to this version's scope.** See Smoke test section — stripped the byte-level BOM so `pytest`/`tomllib` could run at all; no content changed. Flagging since it wasn't something I introduced but I did have to fix it to do any verification.

- **`_validate_sqlite_file`'s schema check is shallow by design** — it only requires the `logs` table to exist (`EXPECTED_TABLES = {"logs"}`), not that every column matches exactly. Full schema-shape validation would require this module to track every migration's column set, which is unnecessary churn for a backup/restore feature whose job is "don't accept garbage," not "enforce exact schema."
- **`retain` is a count, not an age**, per this task's explicit scope note ("prune beyond count") even though ROADMAP.md's own AC4.5 wording says "prunes backups older than the configured count/age" (count-or-age, ambiguous). - **Migration rollback on a mid-migration crash is per-migration, not whole-chain.** If migration 3 of 5 fails, migrations 1–2 stay committed (their `user_version` stamps persist) and the DB is left at version 2, not 0 — this is intentional (retrying only re-runs the failed migration onward, not everything from scratch) but means a truly broken migration function requires a code fix + restart to resolve, not a rollback flag. No migration beyond `_migration_001_baseline` exists yet, so this hasn't been exercised beyond the design.

## How it works

Two independent resilience mechanisms, plus one new coordination point. **Telegram** (`channels/telegram.py:run`) already retried on transport errors; it now backs off exponentially instead of a fixed 5s, so a real outage doesn't tight-loop against a host that's still down, while `self._offset` is untouched by the retry path (it's only advanced inside the per-update loop, which only runs after a poll succeeds) — meaning the very next successful poll picks up exactly where the last successful one left off, no drop, no duplicate. **Ollama** (`llm/ollama_client.py:_post`) gets its own bounded retry for genuine transport failures only (not HTTP error statuses, which mean the host is up and responding, just erroring) — this smooths over a single blip within one request without multiplying latency on a merely-bad response, and updates a public `self.available` flag that's the ground truth for "was the last actual request to this host able to reach it at all."

The new **`core/health.py:HealthMonitor`** is a separate, independent probe (its own periodic `GET /api/version` / `GET .../getMe`, not derived from `OllamaClient.available`) — deliberately decoupled so the "is it up" signal driving user-facing deferral/alerting doesn't depend on whether a chat request happened to fire recently. It tracks UP/DOWN state per service and only acts on *transitions*: an UP→DOWN edge alerts the channel (and always logs, since a Telegram-down alert may itself fail to be delivered — the log line is the documented fallback record), and a DOWN→UP edge on Ollama fires `on_ollama_recovered`. `main.py` wires that callback to `reparse_pending_unparsed`, which pulls every `category='unparsed'` row straight from the DB (persisted, not an in-memory queue) and re-parses each one's original `raw_message` through the normal `parse_message` path, converting it in place via `reclassify_log` and sending a recovery confirmation. Because `handle_inbound_message` checks `health_monitor.ollama_up` **before** ever calling `parse_message`, a message that arrives while Ollama is known down never touches the LLM at all — it's acknowledged and written as `category='unparsed'` (raw text kept verbatim in `raw_message`) immediately, and since `water_total_ml`/`stretch_count`/`diary_count` all filter on the real category strings, an `unparsed` row is automatically excluded from every aggregation while pending, with zero extra filtering logic needed. The one deliberate asymmetry: `reparse_pending_unparsed` is also called **once, unconditionally, at startup** — not only from the health monitor's DOWN→UP callback — specifically so a row deferred by a *previous* process run gets picked up even though this process's `HealthMonitor` starts in the optimistic `ollama_up=True` state and would otherwise never see a transition for it.

## Known limitations

- **`HealthMonitor`'s own reachability signal is independent of `OllamaClient.available`.** They're deliberately two separate probes (one lightweight periodic `/api/version` GET, one derived from real chat-request outcomes) rather than one driving the other — this keeps `core/health.py` decoupled from `llm/`, but it does mean the two can transiently disagree (e.g. a chat request could time out moments before the next periodic health check confirms DOWN). `handle_inbound_message`'s deferral decision uses only `HealthMonitor.ollama_up`, which is the intentional single source of truth for user-facing behavior; `OllamaClient.available` is exposed for now but not yet consumed anywhere else — a natural home for it would be the `/status` command layer (v0.5.0, explicitly out of scope this version per ROADMAP.md's own note).
- **A message that's still genuinely unparseable after Ollama recovers stays `category='unparsed'` forever** (or until a future version adds a way to inspect/discard it) rather than being converted to a terminal "gave up" state or surfaced to the user as a clarifying question. This is a deliberate, minimal choice — no AC specifies the desired end-state for that case, and re-asking a clarifying question for a message that arrived possibly hours earlier risks confusing the user out of context. Flagging as an open design question for whenever the v0.5.0 command/edit layer exists to let the user inspect/dismiss stuck rows.
- **Recovery confirmations don't recompute a running goal total** (unlike the primary `handle_inbound_message` water confirmation, which shows `today X / goal (pct%)`). A deferred message can be re-parsed on a different calendar day than it was sent, so "today's total" would be ambiguous/misleading for it; the recovery confirmation intentionally just states what was recovered (`🔁 Recovered: 500 ml logged from your earlier message.`) without a total.
- **`retry_attempts`/`retry_backoff_seconds` on `OllamaClient` apply per-model, inside the existing v0.2.0 fallback chain** — a 2-model chain with `retry_attempts=2` can, in the worst case (both models fully unreachable), take up to ~2× the configured backoff sum before failing closed. This is bounded (never infinite) but is additive latency on top of the fallback chain's existing per-model timeout; acceptable given it only triggers during an actual outage, which `HealthMonitor`/deferral is already handling for the common inbound-message case by the time the monitor has caught up.
- **No `/status` command surface yet** — per ROADMAP.md's explicit note, that's v0.5.0's command layer. This version's alerting is push-only (channel message on a DOWN transition) plus the log, exactly as scoped.
- Everything from v0.1.0–v0.3.0's Known limitations (LINE stub, Garmin TODO, DB concurrency model, MLX schema-conformance caveat, restore-while-running caveat, count-based backup retention) is unchanged and out of scope here.

## How it works

`commands.dispatch()` runs as a pure, synchronous, LLM-free classification step at the very top of `handle_inbound_message` — before the v0.4.0 Ollama-availability check, before `parse_message`. It either returns `None` (not a recognized command — proceed exactly as v0.4.0 did) or a `Command`. On `kind="undo"`, `main.py` calls `db.last_log()` (most recent non-deleted row, any category); if `None`, it sends `NOTHING_TO_UNDO_MESSAGE` and writes nothing (AC5.2); otherwise it `soft_delete`s that row and sends a confirmation naming what was removed, followed by today's recomputed water/stretch total for water/stretch rows (AC5.1) — the total is already correct because `water_total_ml`/`stretch_count` now filter `deleted_at IS NULL`, so the just-deleted row is automatically excluded with no special-case arithmetic needed. On `kind="edit"`, `main.py` calls `db.last_log(category=command.category)` — the category is decided by `commands.py` from the new value's unit (ml/glass/bottle/liter → water, min/นาที → stretch) — and if found, `update_value`s that row's `value_num` in place (not a new row) and re-confirms the new daily total the same way the primary water/stretch confirmations do (AC5.3); if no matching-category entry exists, it sends `NOTHING_TO_EDIT_MESSAGE` and writes nothing. Because the router is whole-message-anchored and edit targets must parse as a clean `NUMBER [+ UNIT]`, every message in the existing test/smoke corpus (`500ml`, `ดื่มน้ำ 2 แก้ว`, diary sentences, etc.) still returns `None` from `dispatch()` and reaches `parse_message` completely unchanged (AC5.5).

## Known limitations

- **Edit only targets numeric water/stretch values**, decided by the new value's unit (no unit defaults to water ml, matching this version's only specified examples). Editing a diary entry's text, or disambiguating an edit target when the category is genuinely ambiguous, is out of scope — ROADMAP.md's scope note explicitly allows "optional LLM disambiguation only for fuzzy edit targets, validated in code" as a future enhancement; this version's grammar is unambiguous by construction (unit implies category) so it wasn't needed.
- **"Last" for both undo and edit means "most recently inserted, ignoring already-deleted rows" — not "last from today" or "last matching in the current conversation.**" A user who logged water yesterday and hasn't logged anything today, then says "undo last", removes yesterday's entry. This matches the literal reading of AC5.1/AC5.3 ("the most recent … log" / "the last matching entry") and keeps the command's targeting rule simple and predictable; no AC specifies a same-day restriction.
- **No redo.** `soft_delete` is reversible in principle (a future version could add a "redo"/"un-undo" command that clears `deleted_at`), but no command in this version's grammar exposes that — soft-delete was chosen specifically to keep the door open, per Archi's confirmed default, not because redo is implemented now.
- **Confirmations stay English-only**, per this version's explicit scope note — the full bilingual message catalog (detecting the inbound message's language and replying in kind) is v0.6.0. `commands.py` itself is already fully bilingual on the *input* side (Thai and English patterns match equally); only the *output* copy is still hardcoded English, same as every other confirmation in `main.py` today.
- **No `/status`, query, or snooze commands** — those ride this same seam in v0.8.0/v0.9.0 per ROADMAP.md's ordering; this version only implements the two ACs it's scoped for (undo, edit).
