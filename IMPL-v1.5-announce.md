## How it works

`core/release_notes.py` is a standalone catalog (deliberately not part of `core/i18n.py:CATALOG` — per SPEC-v1.5.md §11, release notes are keyed by version string, not message id, so `announce` never collides with the `checkins` module's own i18n keys). `announce_release` is the one control-flow function: it first checks `version in RELEASE_NOTES` and returns immediately (no reads, no writes) if the running version has no entry (AC-22); otherwise it walks `db.active_user_ids()` (pending/blocked users are structurally excluded — they're never in that set), skips a user whose `last_announced_version` already equals `version`, resolves the user's own language via `i18n.resolve_unprompted_language`, and sends. `db.set_last_announced_version` is called **only** after `channel.send` succeeds — every DB read/write and the send itself are individually wrapped in fail-open try/excepts (mirroring `core/reminders.py`'s and `core/access.py`'s own per-operation posture), so one user's DB hiccup or send failure never blocks the fan-out for anyone else, and a failed user is simply retried next startup with no special-casing. `core/access.py`'s one-line addition reuses the exact same `db.set_last_announced_version` primitive so a newly-approved user starts already "caught up" to the version they were approved at, and therefore never receives that (or an earlier) version's announcement on the very next startup.

## Known limitations

- **`main.py` is not wired** (by design — SPEC-v1.5.md §11 places `announce.announce_release(db, channel, config, __version__)`'s call site in the **integration** step, not this module's scope, and the dispatch explicitly said "Do NOT touch: `main.py`"). **Wiring instructions for that step:**
  1. In `core/access.py`'s neighbor, `main.py:async_main`, right after the existing `db.attribute_legacy_to_owner(secrets.telegram_chat_id)` call (main.py, real-run branch — same placement rationale R-N2 states: "the active-user set must be correct first"), add:
     ```python
     await announce.announce_release(db, channel, config, __version__)
     ```
     This must be placed **after** `channel = TelegramChannel(...)` is constructed (a few lines below the attribution call in the current file), so add it there rather than immediately adjacent to `attribute_legacy_to_owner` itself — anywhere after both `db` and `channel` exist and before the scheduler starts is correct.
  2. Add the two imports: `from habit_assistant import __version__` and `from habit_assistant.core import announce` (alongside `main.py`'s existing `from habit_assistant.core import ...` imports).
  3. This call belongs only in the real long-running `async_main` path — not the `--seed`/`--dry-run` one-off CLI branches (which don't construct a real `channel` at all).
- **`__version__` was deliberately NOT bumped to `"1.5.0"`** in `src/habit_assistant/__init__.py` (nor `VERSION` nor `pyproject.toml`'s `version = "1.4.0"`) by this pass. Per SPEC-v1.5.md §6/§11 that bump is listed as happening "at release", which in this project's own PM playbook is Archi's Phase 6.5 step (after Vera confirms every v1.5.0 AC, together with the version-bump + tag + `PROGRESS.md` changelog). Bumping it prematurely, mid-parallel-development, would (a) desync it from the still-`"1.4.0"` `VERSION` file and fail `tests/test_charts.py`'s existing sync-check test, and (b) risk contradicting whatever `checkins`/`preparse`'s own tracks or the shared-surface pass assume about the current version. **Consequence demonstrated by the smoke script above:** until that bump happens, `access.py`'s live catch-up write stores today's `__version__` (`"1.4.0"`), not `"1.5.0"` — so a `/approve` run *right now* would not yet protect a new user from the eventual v1.5.0 announcement. This is correct/inert in the current pre-integration state and self-resolves the moment Archi bumps `__version__` at release — no code change will be needed then. Flagging this explicitly so Archi bumps `__version__`/`VERSION`/`pyproject.toml` together, in the same release commit that wires `main.py` (item above) and lands the `checkins`/`preparse` tracks.
- `core/release_notes.py`'s v1.5.0 entry describes all four v1.5.0 features (check-ins, `/dnd`, faster/offline simple logs, and release announcements themselves) per the dispatch's explicit content list; the exact copy is my own drafting (SPEC-v1.5.md §3.4 gives an illustrative 3-bullet example, not verbatim required text) — flag to Archi/Sophia if different wording is wanted before release.
- No changes were made to `main.py`, `core/commands.py`, `core/i18n.py`, or any `checkins`/`preparse` files, per the dispatch's explicit scope boundary.
