## How it works

Every `category='unparsed'` row now carries a nullable `unparsed_state` lifecycle marker (`NULL`/`'awaiting_llm'` → `'awaiting_clarify'` → `'closed'`, or reclassified away from `'unparsed'` entirely) — migration 013 adds the column with no backfill, so every pre-1.10 zombie row starts life as `'awaiting_llm'` by construction. `pending_unparsed()` only returns rows in that state; the two new `Database` CAS methods (`resolve_unparsed`/`mark_unparsed_state`) are guarded `UPDATE ... WHERE category='unparsed' AND <origin predicate>`, returning `rowcount==1` as `bool` — this is the atomic, single-writer-serialized race guard M1's sweep-vs-tap logic will build on. `Channel.send` now returns the sent message's id; `ReminderState.remember_reminder`/`habit_for_reply` give `core/reminders.py:send_reminder` a bounded per-chat map from reminder-message-id → habit-id, which M2's reply-attribution logic will consult. `pause.is_paused_safe`/`active_pauses_safe` centralize the "read failure ⇒ not paused" fail-open decision that 5 proactive sites (only `reminders.send_reminder` adopted here; the other 4 are M3's scope). `/guide` is now a recognized, reserved command kind with no behavior wired yet. The `reply_to_message_id` parameter is threaded from `TelegramChannel.run` → `on_message` → `handle_inbound_message` as inert plumbing — no code reads it yet.

## Known limitations

- `Channel.send`'s message-id extraction is **defensive** (`resp.json().get("result")` checked for a dict + `"message_id"` key, degrading to `None` on anything else) rather than the spec's literal `str(resp.json()["result"]["message_id"])`. This is a deliberate, documented deviation: several pre-existing tests across `test_channels.py`/`test_charts.py`/`test_garmin.py`/`test_resilience.py`/`test_v18_shared_surface.py` mock a Telegram `sendMessage` response as a bare `{"ok": true, "result": {}}` (they predate R-SS5 and never cared about the return value) — a strict extraction would `KeyError` on every one of them. The real Telegram Bot API always returns `result.message_id` on a successful `sendMessage`, so this changes nothing observable in production; it only avoids an unrelated, large mechanical edit across files outside this pass's stated scope. Flagging this for Vera/Archi in case a stricter reading of R-SS5 is wanted — happy to revert to the literal form and instead patch the handful of pre-existing mocks if that's preferred.
- `core/routing.py`/`core/app.py` were touched **only** for the `reply_to_message_id` plumbing (an unused trailing parameter), per the explicit shared-surface dispatch instruction — even though SPEC-v1.10.md §6/§11 formally assigns `routing.py`/`app.py` to the later, sequential integration seam. No other line in either file was touched; the parallel modules (M1/M2/M3) still never need to edit `routing.py` themselves.
- i18n key-block skeletons are comment-only markers (prefix reservations), exactly mirroring the v1.7/v1.8/v1.9 shared-surface precedent — no `closure_*`/`clarify_*`/`outage_*`/`guide_*` keys exist yet; M1/M2 add their own disjoint keys under those reserved prefixes.
- `pytest-xdist` (R19/AC17) is explicitly **M3's** scope — not installed, not run. The exit bar for this pass was the serial suite only, confirmed green.

## Iteration log

No Vera round yet — this is the initial shared-surface build. Three self-caught regressions during my own smoke pass (not a Vera report), fixed before hand-off:

1. **Failure**: `TelegramChannel.run` now always passes 5 positional args to `on_message`; every pre-existing fake `on_message(chat_id, text, display_name=None, message_id=None)` (16 occurrences across `test_channels.py`/`test_resilience.py`/`test_v18_shared_surface.py`) raised `TypeError`. **Root cause**: the new trailing positional arg is unconditionally supplied by the real caller (mirrors this codebase's existing `message_id`-addition precedent, which required the same mechanical fake-widening at the time). **Fix**: widened every fake's signature to add `reply_to_message_id: str | None = None` (mechanical, `replace_all` per file); also widened `core/app.py:_on_message`'s own closure (the real production call site), which would otherwise have `TypeError`'d on every live inbound message.
2. **Failure**: `tests/test_commands.py::test_reserved_trigger_words_covers_every_real_command_stem` — an exhaustive dict asserting `reserved_trigger_words() == known keys`. **Root cause**: I added `"guide"`/`"คู่มือ"` to the reserved set without updating this test's own ground-truth dict. **Fix**: added `"guide": None, "คู่มือ": "guide"` entries (bare English "guide" is slash-gated like "target"/"heatmap"/"wrapped", so it stays `None`; the Thai alias dispatches).
3. **Failure**: `tests/test_db.py::test_logs_table_created_with_expected_columns`, `tests/test_refactor_s3.py::test_matchers_table_has_all_27_rows_...`, `tests/test_v18_routines_gaps.py::test_migration_011_preexisting_v10_data_byte_identical_after_migration` — three structural/literal-snapshot tests. **Root cause**: a hardcoded `logs` column set, a hardcoded 27-row dispatch-table order, and a byte-identical-migration diff test whose `SELECT *`-based "before" dump predates the new column. **Fix**: added `"unparsed_state"` to the expected column set; inserted `"guide"` before `"query"` in the expected row order; added `unparsed_state: None` to the diff test's "before" baseline with a docstring note explaining why (an additive nullable column isn't a mutation of an *existing* value, which is the test's own stated point).
