## How it works

`core/app.py:async_main` is the one place every LINE module's own piece gets wired together: it picks `LineChannel` or `TelegramChannel` by `config.channel.type`, skips constructing an `OllamaClient`/running the startup probe/constructing a `HealthMonitor` exactly per the no-LLM disposition table (R-B7/B8/B9), registers the digest `CronTrigger` job only on LINE (the other six jobs stay registered unconditionally on both channels since they already self-gate inside `core/jobs.py`), calls `register_rich_menu()` once at startup, and resolves the owner id / validates secrets per the selected channel. The digest itself (`core/digest.py:run_daily_digest`) now accepts the live scheduler and, when a user's own quiet-hours window covers the fire moment, defers their send to that window's end via a one-off `DateTrigger` job instead of sending anyway or dropping it — guarded against redundant re-scheduling by a small in-memory, per-user-per-day marker. `/review` (`core/commands.py` → `core/routing.py` → `core/review.py:execute_review`) closes Module C's own flagged AC25 gap: it sends the weekly review as a free reply, text first, then up to two chart images through the exact same `channel.send_image` media-URL path `/heatmap`/`/wrapped` already use.

## Known limitations

- **`/review` has no Thai bare-word alias** — only the English slash form `/review` is recognized. `digest_review_ready_line`'s own copy points at the literal text "/review" in both languages (pre-existing, Module C's own i18n key), so this is consistent, not a gap against any AC — R-C5 never specifies a Thai alias for this command.
- **The digest quiet-hours deferral uses the real wall clock, not an injectable one** — `core/app.py`'s `_digest_job` closure calls `digest.run_daily_digest(db, channel, config, provider, scheduler=scheduler)` with no `clock=` override (matching every other job closure in this file, none of which are clock-injectable either). This is intentional/consistent, not an oversight, but means the deferral logic itself can only be tested against the real current time (as `tests/test_line_integration.py::test_digest_quiet_hours_deferral_and_once_per_day_guard` does, mirroring `tests/test_refactor_s1_gaps.py`'s own established real-wall-clock-window technique) rather than a fixed historical date.
- **The once-per-day guard (`_DIGEST_DEFERRED_DATES`) only covers the deferral path**, not the ordinary immediate-send path — deliberate, to avoid conflicting with Module C's own `test_run_daily_digest_has_no_internal_dedup_the_scheduler_owns_that` contract (calling `run_daily_digest` twice must still send twice when nothing is deferred). The real "once per day" guarantee for the immediate-send path rests entirely on the single daily `CronTrigger` firing once (APScheduler's own forward-search-on-restart property) plus systemd's single-instance guarantee (TEST-LINE-C.md Finding 2's accepted ruling, now documented in `deploy/habit-assistant-line.service`'s own comment) — not a code-level lock, exactly as that Finding's own recommendation allowed.
- **`--seed`/`--dry-run`/`--test-reminder` CLI flags were made channel-aware for secrets/owner-id resolution** (via `_load_secrets_for_channel`/`_owner_chat_id`) but their own semantics (seeding fake Telegram-shaped data, a manual test-reminder send) remain Telegram-flavored in spirit — none of this is exercised by any AC and none of it is required by SPEC-LINE.md; flagged for completeness, not a gap.
- **A live VPS/Tailscale/real-LINE-console dry-run was not performed** (same limitation every module's own IMPL.md already states — no Linux VPS/systemd/real LINE channel available in this Windows dev environment). Every wiring assertion in this pass is verified against a real webhook server bound to a real localhost port with a real signed HTTP round-trip, which is the closest proof obtainable here.

### Release-gate round (TEST-LINE-integration.md, `tests/test_line_release_gate.py`, 17 new tests, 2 failing)

Archi dispatched Vera's own final release-gate report back to me with 2 release-blocking, journey-level defects (all 30 literal SPEC-LINE.md ACs had already passed; these were found by probing the onboarding/admin cross-module seam beyond the AC list). Both fixed, `tests/test_line_release_gate.py` left byte-for-byte unedited throughout.

- **Finding 1 — `/approve`/`/block`/`/invite` reject every real LINE userId.**
  - **Root cause:** `core/access.py:50`'s `_CHAT_ID_RE = re.compile(r"^-?\d+$")` only ever matched a Telegram-shaped, purely-numeric chat id. Every real LINE `userId` (`"U4af4980629..."`-shaped, SPEC-LINE.md §2.1's own example) is alphanumeric and never matched, so `/approve <line_user_id>` always fell through to the generic `admin_usage` reply instead of approving — onboarding a LINE user through the documented admin surface was structurally impossible.
  - **Fix:** broadened `_CHAT_ID_RE` to a strict two-shape whitelist — `^(?:-?\d+|U[0-9A-Za-z]{16,40})$` — Telegram-numeric (unchanged) OR a `U`-prefixed LINE-shaped token, per Archi's own dispatch. Deliberately NOT hex-restricted (Archi's own suggested `U[0-9a-fA-F]{32}` example doesn't actually match this app's own LINE test fixtures, e.g. `"Ubrandnew0000000000000000000000000"` — `brandnew` contains non-hex letters `r`/`n`/`w` — nor Module A/Integration's own `MEMBER`/`OWNER`/`THIRD` ids, which are 31–33 chars after the `U`, not exactly 32; hex-strictness would have re-broken the very tests this fix needed to pass). One use site (`access.py`'s `target_chat` validation), minimal diff, portable to `main` verbatim (the regex has no LINE-specific import or branch — it's still plain `core/` code, unaware of which channel is running).
  - **Verified against pre-existing tests too**, not just the new one: `tests/test_access.py`/`tests/test_v12_access_gaps.py`'s own malformed-chat-id corpus (`"not-a-chat-id"`, `"abc"`, `"12ab"`, `""`, `"   "`, `"+123"`, `"12.5"`, `"--123"`, `"123-456"`, `None`) — none start with `"U"`, so all still correctly rejected; the existing huge/negative/zero/leading-zero Telegram-id acceptance tests are untouched by construction (the Telegram branch of the regex is byte-identical).

- **Finding 2 — cross-user reply-buffer leak: owner never notified, asker's reply polluted with owner-facing admin text.**
  - **Root cause:** `channels/line.py:_emit` buffered *any* `channel.send(chat_id, ...)` call made during an active reply context, regardless of whether `chat_id` matched the inbound event's own chat_id. `core/access.py:handle_gate`'s owner-pending-approval notification (`channel.send(owner_chat_id, ...)`, fired while still processing a *different* user's own `/start` event) was silently appended to the ASKER's own reply buffer instead of reaching the owner: the owner received nothing at all (no push, no reply), and the asker's own reply leaked owner-facing text verbatim, including the literal `/approve <chat_id>` admin command. The same mechanism would have also swallowed `execute_admin`'s `access_granted` notice to a newly-approved user into the *approving owner's* own reply.
  - **Fix:** `_reply_scope` gained an additive, keyword-defaulted `owner_chat_id: str | None = None` param (stored as `ctx["ownerChatId"]`); `_emit` now buffers only when `chat_id == ctx["ownerChatId"]` (or `ownerChatId is None`, preserving the original "buffer everything" shape for a bare/direct caller with no owning chat_id to compare against — e.g. a hand-rolled test). `channels/line_webhook.py:LineWebhookServer._dispatch`/`process_event` (the one real production call site) now thread the event's own `user_id` through as `owner_chat_id`, so a same-user send still buffers exactly as before (byte-identical common case) and a cross-user send now genuinely pushes, with a `push_ledger` increment on success (per the pre-existing R-A6 rule) — documented in a code comment as correct-and-rare: owner pending-approval/approval notifications now cost push quota.
  - **Test-double compatibility fix (mechanical, not behavioral):** Module A's own `tests/test_line_webhook.py`/`tests/test_line_a_gaps.py` each define a local `_Harness._reply_scope` fake (single-arg `reply_token` signature) used to test `LineWebhookServer` independently of a real `LineChannel`. `_dispatch`'s new 3-arg call shape (`reply_token, owner_chat_id, call`) would have raised `TypeError` against them, so both fakes gained the same additive `owner_chat_id=None` parameter (unused by the fake itself — that comparison lives in `LineChannel._emit`, not the webhook server). Both files' full suites re-verified green (24 + 36 + 49 = 109 tests across `test_line_channel.py`/`test_line_webhook.py`/`test_line_a_gaps.py`, all passing, all of Module A's own direct `_reply_scope(token)` single-arg calls unaffected since `owner_chat_id` defaults to `None`).
  - **Root-cause isolation test reconciled by design, not edited:** `tests/test_line_release_gate.py::test_line_channel_reply_buffer_is_chat_id_blind_by_design` calls `channel._reply_scope("rt-asker-event")` directly (bare, one arg, no owning chat_id) and asserts the ORIGINAL "buffer everything, zero pushes" behavior — this still passes unmodified after the fix precisely because `owner_chat_id=None` is the explicit "no comparison, buffer regardless" escape hatch, while the real webhook path (which always supplies a real `owner_chat_id`) gets the corrected behavior. This was a deliberate design constraint, not a coincidence — verified by inspection before writing the fix, since editing that test file was not an option.
