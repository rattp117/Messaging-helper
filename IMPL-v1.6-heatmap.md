## How it works

`/heatmap [<habit>] [<weeks>]` (Thai: `ปฏิทิน`) is matched by `commands.dispatch` into `Command(kind="heatmap", category=<habit-or-None-or-raw-token>, limit=<weeks-or-None>)`, reusing `/history`'s exact tail-grammar parser (`_parse_history_tail`) — same shape, spec-mandated (§2.1). `main.py`'s integration step (not in my scope, documented below) calls `heatmap.execute_heatmap(command, db=..., channel=..., config=..., registry=..., lang=..., user_id=..., clock=...)`.

`execute_heatmap` first validates `command.category` against the registry (an unresolved token → `heatmap_invalid_habit`, mirrors `history_view`'s `history_invalid_habit`). It then calls `heatmap.render(...)`, which builds a `weeks × 7` grid of fixed 7-day blocks ending at "today" (in `config.app.timezone`, via a private `_today_in_timezone` mirroring `reminders.py`/`query.py`'s own identical helpers) and, for each configured habit (one if filtered, all in registry order otherwise), computes one intensity value per day via `_day_intensity`: goal-bearing (an effective goal exists via `targets.effective_goal`) → `sum_value/goal` clamped to `[0,1]`; goal-less → 1.0 on any entry (`count_true>0` for boolean, `count>0` otherwise) — the exact same branching `core/streaks.py:day_qualifies` already uses, so heatmap's notion of "on track" never diverges from streaks/milestones. This reuses `db.sum_value`/`count`/`count_true` unchanged, which is why soft-deleted rows and `category='unparsed'` rows are excluded for free (those methods already filter them) and every read is `user_id`-scoped (isolation, AC-X3) with zero new DB code. matplotlib renders one `imshow` strip per habit (stacked when unfiltered), with **only digits and English month abbreviations** drawn on the axes (R-H3) — no habit label, bilingual or otherwise, is ever drawn in the image; a regression test (`test_render_language_has_zero_effect_on_image_bytes`) asserts the PNG is byte-identical regardless of `lang`, proving this holds.

On success, `execute_heatmap` sends the PNG via `channel.send_image` with a bilingual caption (habit label(s) + weeks count) and returns `""` — the empty string is the "already delivered, nothing more to send" signal for `main.py`'s wiring. On any failure (matplotlib missing, a render exception, or `send_image` itself raising), it returns a non-empty bilingual text summary (`heatmap_fallback_header`/`heatmap_fallback_line`, "on track N/M days" per habit, computed via `streaks.day_qualifies`) instead — never raises, matching R-3.4/AC-H2's "read-only surfaces never crash" contract.

## Known limitations

- **Grid alignment**: each column is a fixed 7-day block ending "today", not a calendar week aligned to Monday. This is a deliberate simplification (not spec-mandated) that avoids any "future day" masking inside the current partial week — documented in the module docstring. If a strict Monday-aligned GitHub-style grid is wanted later, `_day_grid` is the one function to change.
- **`DEFAULT_WEEKS=12`/`MAX_WEEKS=52`**: the default of 12 is spec-mandated (R-H1); the cap of 52 is my own reasonable bound (spec doesn't mandate a number), mirroring `history_view.py`'s own `DEFAULT_LIMIT`/`MAX_LIMIT` precedent of picking a sane cap without a spec-given figure.
- **Multi-habit row identification**: when no habit filter is given, the PNG's stacked strips carry no in-image row label at all (kept strictly to digits/month-abbreviations per R-H3); the caption instead lists habit order top-to-bottom (`heatmap_caption_all`'s `{habit_list}`).
- **`/help`/`core/review.py` wiring**: `help_heatmap_cmd` (i18n key) and `render()`'s review-attach composability are ready, but actually wiring them into `discoverability.py`/`review.py` is main.py-adjacent integration work outside my owned files (§11) — documented above, not done by me.
- **No new config section**: I did not add a `[heatmap]` config block (spec's §6 "config.toml — `[nudge]` (+ any `[dashboard]`/`[heatmap]` toggles)" makes this optional/conditional). `DEFAULT_WEEKS`/`MAX_WEEKS` are plain module constants, matching `history_view.py`'s own precedent of hardcoding its analogous `DEFAULT_LIMIT`/`MAX_LIMIT` with no config knob.
