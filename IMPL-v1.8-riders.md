## How it works

`[notifications] silent_proactive` (default `True`, defined in the shared surface's `config.py`) is read at each of the three proactive-send call sites and threaded straight into the pre-existing `Channel.send(..., disable_notification=)` keyword the shared surface already added (R-S1) — no new plumbing, no new exception path, no new file. `reminders.send_reminder` keeps its optional `config` param (`None` → stays notifying, matching every pre-v1.8/pre-v0.9 direct caller); `checkins.run_due_checkins` and `nudge.run_due_nudges` both already require `config`, so they read the flag unconditionally. `nudge.py`'s send sits inside its existing two-stage `try/except` fail-open structure unchanged — the flag is read as part of the same call expression, not a new guarded block. No other send site in the codebase (confirmations, replies, the dashboard pin) was touched — proven by `tests/test_riders.py`'s source-sweep guard test, which asserts exactly three `channel.send(...disable_notification=...)` call sites exist in the whole `src/habit_assistant` tree, all three inside the owned modules.

## Iteration log

No Luna↔Vera round happened yet (direct dispatch). While proving the exit bar ("full suite green"), the production change itself surfaced expected, mechanical fallout:

- **Failure class**: after adding `disable_notification=...` to all three send sites, running the full suite showed 92 failures — every one a `TypeError`-shaped failure from a local test fixture named `FakeChannel` (or an inline nested fake) across 15 test files whose `send` override still had the pre-v1.8 narrow shape `async def send(self, chat_id: str, text: str) -> None`. Since `config.notifications.silent_proactive` defaults `True`, and most of these tests construct a plain `Config()`, every one of them now hits a `channel.send(..., disable_notification=True)` call the fake's own method signature can't accept.
  **Root cause**: these fakes predate `channels/base.py`'s `Channel.send(..., disable_notification: bool = False)` addition (v1.8.0 shared surface); Python doesn't enforce ABC method-signature compatibility, so a narrower override compiled fine and only broke at the actual call. This is the exact scenario SPEC-v1.8.md §9's "Decisions" section calls out: *"the one deliberate behavior change vs v1.7: reminder/check-in/nudge payloads gain `disable_notification:true`, so existing proactive-send payload tests must be updated to expect it (intended, documented, config-reversible)"* — except the update needed here is a signature widening, not a content-expectation change, since none of these fakes' `self.sent` records assert on the notification flag at all (they only ever asserted `(chat_id, text)` shape).
  **Fix**: mechanically widened every affected `FakeChannel.send`/local-fake `send` across the 15 files (script-driven regex substitution, three signature-shape variants) to `async def send(self, chat_id, text, *, disable_notification: bool = False) -> None`, mirroring the shared surface's own precedent for widening `on_message` fakes for the trailing `message_id` param (IMPL-v1.8-shared.md, "Files changed" row for `tests/test_channels.py`/`tests/test_resilience.py`). No test file's `self.sent` shape or assertion content changed — every pre-existing assertion (payload text, chat_id ordering, isolation, etc.) still holds unmodified. Full suite re-run: 92 → 0 failures in these 15 files.
- Twelve of these 15 files (`test_adaptive_reminders.py`, `test_checkins_gaps.py`, `test_cli.py`, `test_multi_habit_integration.py`, `test_nudge_gaps.py`, `test_schedules.py`, `test_v09_gaps.py`, `test_v12_integration.py`, `test_v13_integration.py`, `test_v15_integration.py`, `test_v16_integration.py`, `test_v17_isolation_sweep.py`) are **not** in SPEC-v1.8.md §11's `riders` file-ownership row — flagging per Luna's "push back / flag, don't silently patch around" discipline: these were unavoidable, mechanical, zero-semantic-content edits directly caused by my mandated production change to my three owned files, not scope creep into another module's territory (none of them touch `quicklog`/`routines`/`backfill`-owned files).
