## How it works

`tier1_guesses(text, registry, db, config, user_id)` is the one deterministic, zero-LLM entry point: it tokenizes the raw text (each whitespace-split token, plus the whole stripped text), checks each against every numeric/duration/boolean habit's `label_en`/`label_th`/`unit_en`/`unit_th`/alias keys for an exact or length-≥3-prefix match (case-insensitive), derives a value (a number found anywhere in the text, else the habit's `targets.effective_goal`, boolean→1), and separately checks whether the whole text is a bare positive number plausible against each numeric/duration habit's goal window (`config.clarify.plausibility_lower/upper`). Results are unioned exact-before-prefix-before-plausibility, de-duplicated by `(habit_id, value)`, and capped at `config.clarify.max_guesses`. `build_guess_buttons` turns a guess list into `("<emoji> <label> <amount><unit>", "clarify:<row>:<habit>:<value>")` buttons. `offer_clarify`/`send_closure` are thin senders that assume the caller has already won the relevant `mark_unparsed_state` CAS (shared surface) before calling — they only build and send the message, never transition state themselves. `handle_clarify_callback` is the tap handler: it validates the payload shape/bounds (mirrors `quicklog._LOG_CALLBACK_RE`), resolves the habit against the tapping user's own registry, then attempts `db.resolve_unparsed(from_states=('awaiting_clarify',), ...)` — winning sends the exact same `recovered_*` i18n copy `core/routing.py`'s own recovery path uses (mirrored verbatim in a private `_send_recovered_confirmation` helper, to avoid a `clarify.py ↔ routing.py` import cycle — the same rationale `core/undo_ui.py`'s own docstring documents for its `main.py` mirror) plus Undo + a dashboard refresh; losing (another tap or the row was never/no-longer `awaiting_clarify`) sends one friendly `clarify_already_handled` reply and writes nothing.

## Known limitations

- **`_send_recovered_confirmation` is a verbatim mirror, not an import, of `core/routing.py`'s recovery-confirmation branching** (`_send_recovered_generic` + the inline water/stretch/diary special-cases in `reparse_pending_unparsed`). `core/clarify.py` cannot import `core/routing.py` — `routing.py` is the module that will import `core/clarify.py` at the later integration pass (§11), so the reverse import would create a cycle. This mirrors the exact same rationale `core/undo_ui.py`'s own docstring documents for its relationship to `main.py`'s pre-refactor `_execute_undo`/`_describe_log`. Both copies use the identical i18n keys (`recovered_water`/`recovered_stretch`/`recovered_diary`/`recovered_numeric`/`recovered_duration`/`recovered_boolean`/`recovered_text`), so there is no copy drift risk, only a small amount of branching logic duplicated. If a future pass wants a single shared implementation, the natural home is `core/confirmation.py` (already the shared leaf both `routing.py` and `quicklog.py` import for the *ordinary*-log confirmation) — I did not make that change myself since `confirmation.py` isn't in M1's owned-files list and touching it would step outside my assigned scope.
- **AC9's "no guesses" branch has no M1 function** (see the AC9 row above) — this is deliberate per SPEC-v1.10.md §5's interface list, not an oversight; it's a two-line composition of already-existing pieces at the `handle_inbound_message` call site, which is integration's job.
- **Text-type habits are categorically excluded from `tier1_guesses`** (`_GUESSABLE_TYPES = {numeric, duration, boolean}`). Rationale: a text habit's real "value" IS its raw free text, which the `clarify:<row>:<habit>:<value>` callback's number-only value grammar (R9) has no way to carry through a button tap. `handle_clarify_callback` also defensively ignores any (forged/replayed) payload naming a text-type habit id, mirroring `quicklog.handle_log_callback`'s identical existing guard for the same reason.
- **A non-positive label-match-derived value (e.g. a config-authored negative/zero goal) is treated as "no derivable value" and dropped**, not surfaced as a guess — mirrors `core/quicklog.py:_goal_ladder`'s own established "never offer a dead button" guard. Not explicitly required by the spec text, but consistent with R5's "conservative... never a guess the bot can't stand behind."
- **`tests/test_v110_shared_surface.py`, `tests/test_guide.py`, `tests/test_outage_honesty.py`, `tests/test_reply_to_reminder.py`, `tests/test_pause_failopen.py`, and edits to `core/routing.py`/`core/app.py`/`core/checkins.py`/`core/nudge.py`/`core/streaks.py`/`core/review.py`/`pyproject.toml`** are M2/M3/shared-surface's own work, in flight concurrently — not reported on here beyond confirming they don't collide with my files (git status confirms disjoint file sets; my only shared-file edit, `core/i18n.py`, applied cleanly alongside M2's own concurrent edit to the same file, in the pre-reserved disjoint key blocks).

## Iteration log

### Round 1 → Round 2 (Vera's `TEST-v1.10-m1.md` + `tests/test_v110_m1_gaps.py`)

**Finding 1 (CRITICAL) — row-ownership check missing.** `handle_clarify_callback` validated the habit id against the tapping user's own registry but never checked that the *row* (`row_id`) belonged to the tapping chat at all — `db.resolve_unparsed`/`mark_unparsed_state`'s CAS predicate has no `user_id` term (by design, it's shared surface and row-addressed by primary key only). Vera's exploit (`test_CRITICAL_forged_tap_reclassifies_another_users_row_no_ownership_check` + 2 companions): a stranger (`mallory`) forges `clarify:<victim's row>:water:999` — `water` needs no special knowledge (every base registry has it), and a row id is a small guessable sequential integer — and the victim's row got silently reclassified, with the "🔁 Recovered" confirmation + working Undo sent to `mallory`, not the victim.

**Root cause:** `core/clarify.py:handle_clarify_callback`'s own docstring claimed to mirror `core/undo_ui.py:handle_undo_callback`'s ownership pattern (SPEC-v1.2.md R-C3), but only actually mirrored the *habit-id* half of that pattern, not the *row* half.

**Fix (file-local to `core/clarify.py`, no `storage/db.py`/shared-surface signature change):** added `row = db.get_log(row_id)` right after the payload/bounds validation and language resolution (same position `undo_ui.handle_undo_callback` fetches its own row), and treat `row is None or row["category"] != "unparsed" or row["user_id"] != chat_id` as the same friendly `clarify_already_handled` no-op an already-resolved/closed row already produces — line-for-line the `undo_ui.py` pattern Vera cited, collapsing "doesn't exist" / "already handled" / "not yours" into one reply so a stranger learns nothing. Did not thread `user_id` into `db.resolve_unparsed`/`mark_unparsed_state` themselves (shared surface, out of file-local scope, and unnecessary — `user_id` on a `logs` row is immutable once written, so a pre-check has no race window the CAS itself would need to also enforce).

**Finding 2 (secondary) — unbounded raw-message quote.** `send_closure`/`offer_clarify` quoted the full `raw_message` verbatim with no cap, unlike every other budget-conscious formatter in this codebase (`audit_view`/`history_view`, via `core/render_budget.py`). A near-Telegram-max-length deferred message could push the composed closure/offer text well past Telegram's own 4096-char `sendMessage` limit.

**Fix:** added `_QUOTE_MAX_CHARS = 200` + a `_quote(text)` helper in `core/clarify.py` that calls the existing shared `render_budget.truncate(text, max_chars=200)` (reused, not reimplemented — same primitive `audit_view`/`history_view` already use, just with a larger per-value cap than its own 60-char default, since the quoted text is the whole point of these two messages rather than one row among many). Applied at both message-construction call sites (`offer_clarify`, `send_closure`) — **not** to the `text` passed into `tier1_guesses`'s own guess recomputation inside `offer_clarify`, so truncation can never change which guesses get offered. **200 chars** leaves the composed message comfortably under 4096 (a 4000-char raw message now composes to ~397 chars total, per Vera's own re-run below).
