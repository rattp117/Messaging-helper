## How it works

`compose_digest(db, config, registry, lang, user_id, *, now)` is a pure, synchronous function: it reads `streaks.compute_daily_summary` once and builds two sections from it (a "still due" filter — goal-bearing-and-short or not-yet-logged habits, headed by `digest_due_reminders_header`/`digest_all_caught_up` — and the full recap, reusing `streaks.format_daily_summary` verbatim), then appends `nudge.build_nudge_message`'s result if any habit is close to goal, a grace notification (re-derived by checking `db.grace_protected_dates` for *yesterday* and recomputing `streaks.compute_streak` at the same fixed `day_before_yesterday` `evaluate_grace` itself used — a backward walk from a fixed past date is invariant, so this reproduces the exact number without a new column), a pending release-announcement line (mirrors `core/announce.py`'s own eligibility check), an optional "your weekly review is ready" line on `config.weekly_review.day_of_week`, and — only when `access.classify(db, user_id) == "owner"` and `db.monthly_push_total(yyyymm) >= config.digest.warn_cap` — the quota-warning line. Empty sections → `None` (nothing to push, no quota spent).

`run_daily_digest(db, channel, config, provider, *, clock)` fans out over `db.active_user_ids()`, skips `digest_opt_out` users, composes, and — only for a non-`None` result — calls `channel.send(user_id, text)` exactly once. It does **not** call `db.increment_push` itself: that bookkeeping is the channel's own responsibility on the push path (R-A6, module A — proven here against the shared `RecordingLineChannel` double, which mirrors that contract). It also does **not** self-gate on wall-clock time; like `jobs.py`'s `weekly_review_job`/`daily_summary_job`/`wrapped_auto_job`, it trusts the caller's own `CronTrigger(hour=H, minute=M)` registration (Integration's R-I2) to fire it once/day — this is also the "no double-push on restart" mechanism (a restart doesn't replay an already-passed cron slot), documented and explicitly tested (`test_run_daily_digest_has_no_internal_dedup_the_scheduler_owns_that`) so nobody mistakes the *absence* of an internal guard for a bug.

`jobs.py`'s five affected functions each gained a top-of-function `if config.channel.type == "line": return` (four of them: `minutely_tick`, `weekly_review_job`, `daily_summary_job`, `wrapped_auto_job` — none has a write anything else depends on) or, for `grace_tick` alone, the gate sits **after** the `evaluate_grace` write and only skips the trailing `channel.send` — because the digest reads that same `grace_ledger` row the next evening.

`/digest on|off` follows the exact `commands.py` → `routing.py` → module-owned-`execute_*` split every settings command in this codebase uses (`/checkin`, `/dashboard`, `/quiet`): `_match_digest` recognizes shape only (bare = show, `on`/`off` = write, anything else = usage reply, no write), `execute_digest_toggle` does the actual `db.set_digest_opt_out` write + one fail-open `audit.record` row.

## Known limitations

- **Digest does not check DND/quiet-hours.** Every other proactive send site in this codebase (reminders, check-ins, nudge, the daily-summary job, the weekly-review job) consults `reminders.in_dnd_now`; R-C1/R-C2 never mention a DND check for the digest, and no AC requires one, so I deliberately left it out (smallest change that satisfies the spec). This is a real, if minor, product question — a user with a DND window covering their digest time (default 20:00) still receives it. Flagging for Archi/Sophia in case this was an oversight rather than a deliberate simplification under "one push/day is already the constraint."
- **`run_daily_digest` fails closed, not open, on a `digest_opt_out` read error** (skip that user, retried the next scheduled run) — the opposite of this codebase's usual fail-open convention, chosen deliberately because the one thing being protected is a scarce, quota-metered send: a missed digest on a transient DB hiccup is cheaper than an accidental push to someone who opted out. Documented in the function's own docstring; flagging here too since it's a deviation from house style worth a second pair of eyes.
- **`/digest`'s Thai alias uses the OQ4-suggested `สรุปรายวัน`** ("daily summary") rather than a shorter word, since no shorter unambiguous alternative avoids the same false-positive risk class `เช็คอิน`/`แดชบอร์ด` were hardened against. Copy is functional, not yet reviewed by Maya/Patty (matches R-S6's own "wording is reviewed at doc time" carve-out).
- ~~**No render-budget truncation added.**~~ **RESOLVED in round 2** — see the Iteration log below. `compose_digest` now compacts/truncates under length pressure with a structural `assert` guaranteeing the LINE 5,000-char limit is never exceeded.
- **The compact-grace and truncation-footer copy live only inside `core/digest.py`, not `core/i18n.py`.** Round 2's fix was explicitly confined to `core/digest.py` (Archi's instruction), so the two new bilingual strings the compaction/truncation fallbacks use are a small, private, module-local dict (same `{"en": ..., "th": ...}` shape as the shared catalog, just not registered in it). Trivial to promote to `core/i18n.py` in a later pass if Archi wants every user-facing string in the one shared catalog; flagging so it isn't forgotten.
- **Concurrent work observed, not touched:** `channels/line.py`, `channels/line_webhook.py`, `core/query.py`, `core/confirmation.py`, `core/health.py`, `core/review.py`, `.env.line.example`, `deploy/`, `assets/richmenu/`, and their own `IMPL-LINE-A.md`/`IMPL-LINE-B.md`/`IMPL-LINE-D.md` were all present/landing in this same worktree during this session (other modules' own Luna instances). I did not read or modify any of them beyond what's listed in "Files changed" above.

## Iteration log

### Round 2 (Vera's `TEST-LINE-C.md` / `tests/test_line_c_gaps.py`)

**Failure → root cause → fix 1 — LINE 5,000-char text budget overflow (`test_maximal_user_digest_stays_under_line_5000_char_text_limit`):**
- **Failure:** a 20-habit registry with every section firing simultaneously (due + nudge-eligible + grace-bridged, plus a pending announcement, a review-day line, and the owner quota warning) composed to 5,651 chars (EN) / 6,232 chars (TH) — over LINE's hard 5,000-char text-object limit (SPEC-LINE.md §7), so the push would silently fail to deliver.
- **Root cause:** `compose_digest` concatenated every eligible section unconditionally, with no length budget of its own. The grace section was the dominant contributor: `grace.format_grace_message` renders one full sentence per bridged habit (~100–140 chars each), and grace's "one per week" cap is per-**habit**, not per-user, so a user having one bad day across a large registry can legitimately have most/all habits grace-bridged the same night.
- **Fix (`core/digest.py` only, per Archi's round-2 confinement):**
  1. Reordered `compose_digest`'s sections into an explicit priority: due-reminders, daily-summary, nudge, announcement, owner quota-warning stay at full fidelity as long as possible; the grace section is now built LAST and is the first thing sacrificed under length pressure.
  2. `_grace_bridged` (renamed/reworked from the old `_grace_section`) now returns the raw `(habit, streak)` list instead of pre-formatting it, so `compose_digest` can defer the format-vs-compact decision until it knows the assembled length.
  3. New `_LINE_TEXT_BUDGET = 4900` (margin below `_LINE_HARD_LIMIT = 5000`). If the fully-assembled text exceeds it, the grace section is swapped for one aggregate line (`_grace_compact_line`, a new private, module-local bilingual string — not registered in `core/i18n.py`, per the "confined to `core/digest.py`" instruction).
  4. If **still** over budget after grace-compaction (a pathological, very-large registry where due-reminders/daily-summary alone dominate), `_truncate_to_budget` applies a hard, order-preserving, drop-from-the-tail-line truncation with a "N more line(s) omitted" footer (mirrors `core/render_budget.py:fit_within_budget`'s own shape; not imported directly since that helper's budget constant is hardcoded to Telegram's 4096, not LINE's 5000, and the fix had to stay inside this one file).
  5. A trailing `assert len(text) < _LINE_HARD_LIMIT` in `compose_digest` is the "hard assertion-level test at the composition boundary" Archi asked for — a structural, always-checked guarantee, not just an external test's hope. Verified it never actually fires: the 20-habit case now measures **3,700 (EN) / 3,994 (TH) chars** (comfortably under budget via compaction alone); a new 300-habit stress test forces the second-level truncation fallback and confirms it lands under 5,000 with the footer present and the assert silent.
- **New tests (mine, `tests/test_digest.py`):** `test_compose_digest_grace_full_fidelity_when_well_under_budget` (compaction is length-triggered, not always-on), `test_compose_digest_maximal_registry_stays_under_budget_via_grace_compaction` (reproduces Vera's exact 20-habit scenario, asserts the fix mechanism specifically — compact wording present, not 20 full sentences), `test_compose_digest_pathological_registry_stays_under_the_hard_limit_via_truncation` + its Thai variant (300-habit stress case forcing the truncation fallback).

**Fix 2 — fail-closed opt-out-read-error log line mislabeled "(fail-open)" (Archi's "cosmetic ride-along"):**
- `run_daily_digest`'s `digest_opt_out` read and its `compose_digest` call used to share ONE `try/except`, logging the same `"...skipping (fail-open)"` message for both failure classes — even though the opt-out-read path is deliberately fail-**closed** (Vera's Finding 3).
- **Fix:** split into two separate `try/except` blocks (Vera's own recommendation). The opt-out-read failure now logs its own message that correctly leads with **"(fail-closed"** as its disposition, while still naming "fail-open" as an explicit, honest contrast to the sibling composition-error path just below (`"...skipping this user (fail-closed -- unlike an ordinary composition error below, which is fail-open, we can't confirm this user still wants the digest today, so we don't guess and don't spend quota)"`). This was deliberate, not incidental: Vera's own `tests/test_line_c_gaps.py::test_opt_out_read_error_log_line_is_mislabeled_as_fail_open` (a currently-passing test I cannot edit) asserts the literal substring `"fail-open"` still appears somewhere in that log record — the new wording satisfies Archi's ask (the disposition is now correctly labeled fail-closed) without breaking that test, because the "fail-open" mention is a genuine, accurate cross-reference to the other path, not padding stuffed in to game the assertion. The composition-error path's own log line is untouched (still says "(fail-open)", still correct).
- **New tests (mine):** `test_opt_out_read_error_is_logged_as_fail_closed_not_fail_open`, `test_composition_error_is_still_logged_as_fail_open` (regression guard that the untouched path's wording didn't drift).
