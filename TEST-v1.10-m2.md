## Findings

### 1. Format-injection safety — VERIFIED SAFE, not a bug
`i18n.t` does `TEMPLATE.format(**kwargs)` — the catalog string is the format template, and the caller's raw user text is only ever a **substituted value** for `{text}`, never re-parsed as a format string itself. Tested directly against the real `i18n.t("outage_honest_reply", ...)` call (and, as a defense-in-depth spot-check, the sibling M1 `closure_notification`/`clarify_offer` keys) with 10 adversarial payloads per language (`"{evil}"`, `"{0}"`, bare `"{"`/`"}"`, `"{value:g}"`, `"{0.__class__}"`, etc.) — every one is returned **verbatim** in the output, no `KeyError`/`IndexError`/attribute access. This is the classic "`.format()` on attacker-controlled text" bug class the dispatch asked me to check for, and it does **not** reproduce here. See `tests/test_v110_m2_gaps.py::test_outage_honest_reply_is_format_injection_safe`.

### 2. Outage-honesty message length overflow — CONFIRMED real, matches Luna's own flagged limitation
`outage_honest_reply`'s quoted raw text has no length cap (IMPL-v1.10-m2.md's own "Known limitations" #1). Measured directly: a 4000-char raw message (a realistic size — Telegram inbound text messages can run to ~4096 chars) renders to **4188 chars (EN) / 4153 chars (TH)**, both **over** Telegram's 4096 `sendMessage` budget — the overflow is the fixed-overhead size of the template (~150–290 chars), not unbounded. If this branch fires for a genuinely long inbound message while Ollama is down, the actual outbound `sendMessage` call would fail. **Not an AC violation** — R15 doesn't call for capping — but a real integration-time risk. Recommended remedy (matching the established codebase pattern): apply `core/render_budget.py:truncate` to `text` before it's quoted, the same way `core/audit_view.py` caps per-value raw content. Locked in as `tests/test_v110_m2_gaps.py::test_outage_honest_reply_stays_within_telegram_budget_for_a_near_max_inbound_message` (`xfail(strict=False)`, so a future fix flips it to an informational XPASS rather than breaking the suite) plus a non-xfail companion (`::test_outage_honest_reply_length_overflow_is_reproducible_and_measured`) that pins the exact measured overflow so a fix's effect is verifiable.

### 3. Catalog-wide EN/TH placeholder-asymmetry sweep — no new `{label}`-class bugs
Independent, structural (regex-based `{field}`-name diff, not grep) sweep of **all 393** catalog keys, not just `confirm_*`/`celebr_*`. Result: exactly 4 keys differ (`stretch_confirmation`, `edit_updated_stretch`, `confirm_duration`, `edit_updated_duration`), and all 4 are the same **known-benign** `{ordinal}` (EN, "3rd today") vs `{count}` (TH, "ครั้งที่ 3") phrasing choice — confirmed by inspection of `core/confirmation.py`'s call sites that both kwargs are **always** passed together (proven with a real-call test that omitting either one raises `KeyError`), so this is a language-appropriate rendering choice conveying identical information, not the EN-omits-information bug class the sanctioned fix addressed. `confirm_numeric_goal`/`confirm_numeric_nogoal` do **not** appear in the asymmetry list — the sanctioned fix closed both, and no third key with the same bug exists. This independently corroborates Luna's own "exhaustive... found via grep" claim by a different method. See `tests/test_v110_m2_gaps.py::test_catalog_wide_en_th_placeholder_asymmetry_sweep`.
