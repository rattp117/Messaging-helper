## Notable findings during this pass (all resolved before this report)
1. **My own first-draft precision bug, not a product bug:** the weekly review's own header (`weekly_review_header`) and the trends block's own header (`trends_review_header`) both happen to start with the same "📊" emoji — my first draft used that shared emoji to locate the trends section and matched the review's own header instead (index 0 for both). Fixed by using `trends_review_header`'s exact catalog string, which is unique to the trends block.
2. **`db.last_log(...)` excludes soft-deleted rows** (by its own long-standing, correct contract) — my first draft of the raising-refresh test called it right after an undo and got `None` back. Fixed by capturing the row id before the undo and looking it up directly via `db.get_log(row_id)` afterward.
3. **The dashboard's own render-cache (R-D3) correctly suppressed a second edit in my choreography test's final step** when the day-rollover refresh immediately followed a `/target` refresh with nothing else having changed in between — genuinely correct behavior (avoiding a redundant Telegram edit call), not a missed trigger. Adjusted the assertion to confirm the rollover ran and the board content is verifiably current, rather than insisting on a literal second edit call that R-D3 legitimately prevents.
4. A fake-channel-only artifact: two independently-constructed `_ScriptedChannel` instances (simulating two separate process runs against the same persisted DB) generate colliding pin-id strings, since each starts its own id counter from the same base — not a real bug (real Telegram message ids are globally unique and monotonic regardless of process restarts), just a test-double simplification. Adjusted the button-undo test to assert on the meaningful signals (edit attempted against the persisted id, self-heal produced a live pin) rather than id inequality.
