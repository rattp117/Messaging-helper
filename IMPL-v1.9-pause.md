## How it works

`core/commands.dispatch` recognizes `/pause [<habit>] <Nd|until DATE|until WEEKDAY>` and the Thai aliases `พัก`/`หยุดพัก`, plus `/resume [<habit>]` and `กลับมา`/`ต่อ`, producing a `Command` that carries the raw habit token (`category`, `None` = all habits) and raw duration tail (`pref_value`, `None` = "show status"). `core/pause.py:execute_pause` resolves the habit against the registry, parses the duration (`<N>d` → today + N‑1 days; `until YYYY-MM-DD`; `until <weekday>` → the next future occurrence), rejects a past/unparseable date (`pause_invalid_date`) or an over-cap span (`pause_too_long`, default 30 days), then **replaces** any existing pause for the exact same scope (`db.clear_pauses` then `db.insert_pause`) and writes a `pause_set` audit row. `execute_resume` deletes the pause row(s) exactly scoped to the given habit (or every scope present, for a bare `/resume`) and writes `pause_clear`. `is_paused(db, config, user_id, habit_id, when)` — the helper integration will wire into `reminders`/`checkins`/`nudge`/the weekly-review and daily-summary jobs — walks `db.active_pauses(user_id)` and returns true when any row (habit-scoped or all-habits, `habit_id IS NULL`) covers `when`. Nothing in this module touches the engine's own NEUTRAL classification (`streaks.classify_day` already treats a paused day as NEUTRAL unless it also carries a real log, in which case `day_qualifies` wins per R16) or any reactive-milestone path.

## Known limitations

- **`/resume <habit>` does not split an active all-habits pause.** R13 says `/resume [<habit>]` "deletes the user's active pauses rows for that habit" — read literally as rows *keyed* to that habit. If only an all-habits pause is active, there is no habit-scoped row to delete, so `/resume gym` returns `pause_none_active_habit` and gym remains paused via the untouched all-habits row. The alternative (splitting the NULL-scope row into N‑1 explicit per-habit rows for every other habit) is a materially larger, unspecified feature the storage schema doesn't naturally support; I chose the literal, minimal-scope reading and documented + tested it explicitly (`tests/test_pause.py::test_pause_all_then_resume_one_leaves_it_covered_by_the_all_row`). If product wants the "smart split" behavior instead, that's a one-function change in `execute_resume` — flagging for Archi/Vera rather than guessing.
- **Overlapping-pause policy is "extend/replace," not "reject" or "stack."** A second `/pause` for the exact same scope (same habit, or same all-habits key) always replaces the prior window rather than erroring or creating a second row — not explicitly mandated by SPEC-v1.9.md §4, but the only policy that keeps `active_pauses` from accumulating stale duplicate rows for the same scope over a user's lifetime, and keeps `/resume`'s own "delete the row(s) for this scope" simple and correct. Documented in `core/pause.py:execute_pause`'s own docstring and tested (`TestAdversarialOverlapAndScope`).
- **Thai alias triggers (`พัก`/`หยุดพัก`/`กลับมา`/`ต่อ`) never bare-match.** Unlike `เช็คอิน`/`แดชบอร์ด`'s established "bare word = show" precedent, these four require a mandatory non-empty tail — a deliberate, stricter safety choice for `ต่อ` in particular (an extremely common two-character Thai word for "continue/next"). R13's "no token resumes all" meaning stays fully reachable via `/resume` (the English slash form); it's just not reachable via a bare Thai word alone. This also means `tests/test_commands.py`'s existing `_RESERVED_WORD_EXPECTED_KIND` table needed **zero edits** — every reserved pause/resume word still dispatches to `None` when typed bare, exactly as that shared test already expected before this module landed.
- **`/pause` bare / habit-only-no-duration "show status" reply is a UX addition, not AC-mandated** — R12's own grammar always pairs a duration with an (optional) habit. I chose to show current status rather than an error, mirroring `/remind`'s/`/checkin`'s own "empty tail → read-only status" convention elsewhere in this codebase. Flagging so Vera doesn't mistake it for an AC gap.
- **No engine/streaks.py changes** — the pause NEUTRAL classification, the daily walk, and the weekly (cadence) walk were all already built by the shared-surface pass; this module only writes to the `pauses` table through the already-existing read accessors those walks consult. `tests/test_pause.py::TestEngineIsoWeekBoundaryNeutral` proves the ISO-week-boundary interaction end-to-end through this module's own `insert_pause`, not raw SQL.
- **One full-suite failure exists, but it is not in this module's files.** This module was built in parallel with `cadence`/`grace`/`wrapped` (SPEC-v1.9.md §11), each editing disjoint regions of the same shared files (`storage/db.py`, `core/commands.py`, `core/i18n.py`); I re-read each shared file immediately before every edit to confirm I never clobbered a concurrent module's work. The full suite is at **4086 passed / 1 failed / 1 skipped / 1 xfailed** — the single failure is `test_reserved_trigger_words_covers_every_real_command_stem` on the reserved word `สรุปเดือน`, caused by module `wrapped`'s own dispatch wiring, not `pause`/`resume`. See "Smoke test done" above for the full trace. AC3's gate (no pause rows → unchanged behavior) is unaffected — this module writes to a table (`pauses`) that stays empty unless `/pause` is actually invoked.

## Iteration log

### Round 2 — Vera's `TEST-v1.9-pause.md`, 3 findings, all fixed

**Finding 1 (serious) — early-resume retroactive un-protection (R13/R14 tension).**
- *Failure:* `test_early_resume_before_natural_expiry_matches_natural_expiry_result` — a streak logged Mon–Wed, paused Thu–Fri, logged Sat–Sun, then `/resume gym` called *before* the pause's natural expiry. `compute_streak` dropped from the expected 5 to 2.
- *Root cause:* `execute_resume` always called `db.clear_pauses` — a hard `DELETE` — regardless of whether the pause row had already started accumulating protected (elapsed) days. Deleting a row that covered *already-passed* dates retroactively un-protected them for any later `compute_streak` walk, breaking R14's "after resume the streak continues across the paused gap" promise whenever `/resume` fired before `end_date`.
- *Fix (Archi ruling: implement Vera's suggested truncate approach):* Added `db.truncate_pause(user_id, habit_id, new_end_date)` (`storage/db.py`, pause write region) — an `UPDATE ... SET end_date = ? WHERE ... AND end_date > ?`, so it only ever pulls a row's end date backward, never extends it, and no-ops on a row already ending on/before the target. Added `core/pause.py:_resume_scope(db, user_id, habit_id, today)`, the new single decision point both the habit-scoped and bare-all `/resume` paths now route through: it finds the (at most one, per the extend/replace invariant) row currently covering `today` for that scope; if the row hasn't started yet (`start_date > yesterday`, i.e. paused today with zero elapsed days — Archi's explicit "full delete is fine" carve-out) it calls `db.clear_pauses` as before; otherwise it calls `db.truncate_pause(..., yesterday)`, leaving every already-elapsed paused date intact and NEUTRAL-protected while ending the pause from today onward. `execute_resume` gained a `clock=datetime.now` parameter (mirrors `execute_pause`'s own convention) so it can compute "today"/"yesterday" — no existing caller passes it (AC20's proactive-suppression wiring is still integration's job, unstarted), so this is purely additive. Rows that don't currently cover `today` at all (already naturally expired, e.g. Vera's own `test_expired_pause_row_does_not_linger...`) are left untouched by `_resume_scope` (returns 0, no write) — they were never blocking anything and `is_paused`/`paused_dates` already exclude them by date range, so no further "excluded from active listings" work was needed beyond that existing date-range filtering.
- *Verified:* `test_early_resume_before_natural_expiry_matches_natural_expiry_result` now passes (streak == 5). Confirmed the same-day-start case still fully deletes (`tests/test_pause.py::test_resume_habit_deletes_row_and_confirms` — pause set and resumed on the same `today`, `db.active_pauses(OWNER) == []` afterward, unchanged/green).

**Finding 2 — untruthful `/resume <habit>` reply when an all-habits pause still covers it.**
