## Judgment calls (per dispatch's adversarial angles)

### Admin re-approve of an already-active user records a "no-op-looking" row (not a bug)
`core/access.py:execute_admin`'s approve branch (lines 287–311) always calls `db.upsert_user(target_chat, status="active")` then always calls `audit.record(...)` after it succeeds — it never compares the pre-read `previous_status` to `"active"` first. Re-approving an already-active user therefore writes a `user_approve` row with `old_value == new_value == "active"` (`test_admin_reapproving_an_already_active_user_still_records_a_row_by_design`, PASS as a documentation test).

This is **consistent with the spec as written**, not a violation:
- R-C1: "Each execute path calls `audit.record(...)` immediately after its successful DB write" — no conditional-on-actual-change clause.
- AC-C7's "not audited" carve-out (§2.2) lists only **read-only** commands (`/habits`, `/users`, `/help`, `/audit`, a target/remind *show*, an NL query) and plain log creation — an admin approve/block is a state-changing command by nature, even when the particular invocation happens to be a no-op on this occasion.

Contrast with `handle_gate`'s own no-op path (`test_handle_gate_active_user_never_records_anything`): an already-active chat's message short-circuits at the function's very first `if access in ("owner", "active"): return True` — before any DB write or `record()` call — so genuinely zero rows are written there. The two "no-op" shapes are different: `handle_gate` never reaches a write at all for a no-op; `execute_admin`'s approve/block always performs the write (idempotent at the DB layer — `upsert_user` is itself idempotent) and therefore always audits it. **Flagging for Archi/Sophia as a design note, not a defect** — if the owner re-running `/approve` on someone already active should be silent, that would need an explicit spec amendment (compare `previous_status == "active"` before writing/recording); as written, the spec does not ask for that comparison.

### `undo_ui.send_undo_confirmation` has no try/except around `db.soft_delete`
Unlike the other four capture sites (`targets_command`, `schedules`, `preferences`, `access`), `send_undo_confirmation` calls `db.soft_delete(row["id"])` unguarded — a failure there propagates as an uncaught exception rather than degrading to a friendly reply. This is **pre-existing v1.1 behavior, not introduced by v1.3** (confirmed: the audit `record()` call sits strictly after the unguarded `soft_delete` call, so it is never reached on a primary-write failure — `test_undo_primary_soft_delete_failure_writes_no_audit_row` confirms the load-bearing property, "no audit row for a failed write," still holds even though the failure mode differs in shape from the other four modules'). Not a v1.3-capture defect; noting only because the dispatch's "reverse fail-open direction... at every site" angle surfaced the asymmetry. Out of this pass's scope to fix (no production-code changes).

### `tests/test_audit_view.py::test_render_recent_50_rows_of_realistic_remind_edits_exceeds_telegram_limit`
- **Owning module:** `audit-view` (not `audit-capture`) — file never touched by this pass or by Luna's `audit-capture` implementation.
- **What it found:** at 50 rows of realistic remind-time edits, `audit_view.render_recent` produces a 5,828-character reply, over Telegram's 4,096-char `sendMessage` limit. The test's own docstring states it is "Expected to FAIL until Luna adds either per-value truncation... or reply chunking" and references a `TEST-v1.3-view.md` report that does not yet exist in this tree — indicating the `audit-view` track's own Vera pass authored this as a deliberate, self-documented finding and has not yet closed the loop with that module's Luna.
- **Action:** route to the `audit-view` module's own Luna↔Vera pair, not to `audit-capture`. Flagging here only because the dispatcher's stated baseline ("1440 passed / 1 skipped — must not regress") is technically not met by the *full repo* run; `audit-capture`'s own 57 tests are unaffected and independently green.
