## How it works

`handle_inbound_message` now tries `preparse.deterministic_parse(text, registry)` immediately after command dispatch returns `None`; a hit skips straight to the shared confirmation-building code (same `result` variable, same downstream branches as the LLM path — this is what keeps AC-14's confirmation byte-identical), bypassing both the health-monitor deferral check and the target-NL gate, so a whole-message "500ml"-shaped log works even while Ollama is down (AC-16). A miss falls through to the pre-v1.5 deferral→target-NL→`parse_message` sequence unchanged. `checkins.run_due_checkins` now runs on its own `checkin_tick` job on the same minutely cadence as `reminder_tick`; `"checkin"` commands route to `execute_checkin`, which now also calls `audit.record` after every successful write, using three new closed-vocabulary actions that mirror `remind_set`/`remind_off`/`remind_default`'s own three-way shape. `announce.announce_release` runs once at real startup, after attribution and before the scheduler starts, skipped by every one-off CLI branch. Separately, `core/units.py:build_unit_lookup` — shared by `preparse`, `commands._parse_edit_value`, and `commands._parse_target_value` — now detects a unit token claimed by two *different* habit ids and excludes it from the lookup entirely, rather than silently picking whichever habit was registered first; this is inert against the shipped default registry (water/stretch/diary have no colliding units) and only changes behavior for a hypothetical future `[[habits]]` addition that reuses an existing unit string.

## Regression root-cause note (for Vera's awareness)

Wiring `deterministic_parse` into `handle_inbound_message` surfaced a class of pre-existing test breakage that had nothing to do with a wiring mistake: several tests across `test_commands.py`, `test_fallback.py`, `test_v11_integration.py`, and `test_v12_integration.py` used a bare "500ml"/"300ml"-style message as their test input while relying on a **mocked, hand-ordered `chat_json` response queue** (`responses.pop(0)`-style fakes) to control what gets logged. Once "500ml" started resolving via `deterministic_parse` (AC-14, by design), it stopped consuming a queue entry at all — every test whose queue accounted for it desynced, either logging the WRONG category/value (the next queued fixture, meant for a later message) or never reaching the LLM assertion it meant to exercise (confidence threshold, total-outage fail-closed, deferral). Every one of these was a **test-fixture staleness** issue, not a production bug: each was fixed by either (a) changing the input message to a shape `deterministic_parse` doesn't match (e.g. "drank some water"), preserving the test's original intent, or (b) removing the now-unconsumed queue entry. Three of these got a companion test added right next to the fix (two in `test_commands.py`, one in `test_v11_integration.py`), proving the NEW (AC-14/AC-16) behavior directly rather than just removing coverage. Worth watching for the same pattern in any test Vera adds against a "NUMBER UNIT"-shaped fixture message going forward.

## Known limitations

- **Reported, not silently changed** — `core/units.py:build_unit_lookup`'s collision-exclusion fix is shared by all three consumers (`preparse.deterministic_parse`, `commands._parse_edit_value`, `commands._parse_target_value`), per R-L5's "one shared function, no duplicated unit logic" mandate. For `_parse_edit_value` (a bare "NUMBER UNIT" edit command with no habit named), this is a straightforward safety improvement, structurally identical to `deterministic_parse`'s own fix. For `_parse_target_value` (`/target <habit> <value><unit>`, where the habit IS explicitly named), the semantics genuinely change: previously, a colliding unit token would succeed when the *named* habit happened to be the first-registered claimant (and correctly reject via the existing R-T9 cross-check otherwise, so it never silently misattributed to the wrong habit — only sometimes usability-failed when the named habit was second). After this fix, `/target <habit> <value><colliding-unit>` now **always** returns `target_action="usage"` when any collision exists for that unit, regardless of which habit is named or its registration order. This is inert against the shipped default registry (no collisions exist), and does not violate any acceptance criterion — flagging it here per the coordinator's explicit "report, don't silently change" instruction rather than deciding unilaterally whether `/target`'s own cross-check should special-case an explicitly-named habit to bypass the exclusion. If a future `[[habits]]` config intentionally wants two habits to share a unit token AND `/target` to still resolve it when the habit is named explicitly, that's a design question for Archi/Sophia, not something this pass decided on its own.
- **`config.toml`'s live `[health] interval_seconds`/`[ollama] probe_on_startup`** were already landed as config fields in the shared-surface pass (`IMPL-v1.5-shared.md`); this pass adds the actual runtime *gate* around the schema probe (AC-18) but does not change `HealthMonitor`'s own interval wiring, since `main.py` already read `config.health.interval_seconds` before v1.5.0 (AC-17 was already structurally satisfied; not touched by this pass).
- **`checkins.run_due_checkins`'s `clock` parameter** shares the same Python default-argument late-binding characteristic already documented for `in_dnd_now`/`send_reminder` (`IMPL-v1.5-shared.md`'s own "Known limitations"): `main.py`'s `checkin_tick` job omits `clock=` (correct for production — it should react to the real wall clock), so a test driving the tick through the real scheduler wiring cannot rely on monkeypatching `checkins.datetime`. `tests/test_v15_integration.py`'s check-in section works around this by calling `checkins.run_due_checkins` directly with an explicit `clock=` (pinned to a controlled hour, but anchored to `datetime.now()`'s own real date so it lines up with the real-clock-timestamped log rows the scripted `/checkin on`/log messages wrote) — the setter is exercised through the real command-routing wiring; only the tick's timing is made deterministic this way, mirroring the codebase's established discipline.
- `announce_release`'s TOCTOU race under truly concurrent invocation remains an accepted, documented limitation (Archi's ruling, PROGRESS.md 2026-08-23) — `xfail(strict=False)`, not fixed, per this pass's explicit instruction.
